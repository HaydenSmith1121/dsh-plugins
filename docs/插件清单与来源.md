# 目录配置文件格式与来源

**[← 回到首页](../README.md)**

> 本页回答两件事：**插件的版本 / sha256 / 安装说明去哪看**，以及
> **市场仓库里 `catalog/plugins/<slug>.json` 每个字段是什么意思、谁写的**。
>
> 旧的「11 个打包插件清单 + tarball 校验表」已经不在这里了 —— 插件本体搬去了
> [`HaydenSmith1121/dsh-plugin-collection`](https://github.com/HaydenSmith1121/dsh-plugin-collection)，
> 逐插件的版本、sha256、作者、上游仓库、许可与安装说明以**那边**为准（见第一节）。

<a name="where"></a>

## 一、插件事实去哪看

| 想知道什么 | 去哪看 |
|---|---|
| 有哪些插件、各自什么版本、sha256、字节数 | 集合仓库 [`README.md`](https://github.com/HaydenSmith1121/dsh-plugin-collection/blob/main/README.md)（总表）与 [`manifest.json`](https://github.com/HaydenSmith1121/dsh-plugin-collection/blob/main/manifest.json)（机器可读，派生） |
| 某个插件的权威事实（版本列表 / 状态 / peer 结论 / 备注） | 集合仓库 `plugins/<id>/plugin.json` |
| 某个插件怎么装、怎么配、怎么卸 | 集合仓库 `plugins/<id>/README.md` |
| 某个插件在**市场里**按什么方式安装、装之前会提示哪些事实 | **本仓库** `catalog/plugins/<slug>.json`（格式见第二、三节） |
| 哪些第三方插件的实测记录是人工核对的、证据是什么 | 本仓库 [`catalog/overrides/curated.json`](../catalog/overrides/curated.json) |

**本仓库不再分发任何第三方插件的字节**，也不再重新打包自研插件：市场里安装时是
按配置文件里的 `install.method` 去上游取（`github:owner/repo` 或 npm），自研插件的 tarball
由集合仓库托管。原先随本仓库打包的四个第三方插件（`@dsh-market/plugin`、
`dsh-workbuddy-connect`、`dsh-connect-trae`、`dsh-receipt`）的 tarball 已全部删除：
`dsh-workbuddy-connect` 与 `dsh-connect-trae` 现在按公开索引里的干净规格解析为 npm 方式安装；
采不到干净规格的插件不会出现在目录里 —— 市场不会假装能装一个没有安装方式的插件。

## 二、一份配置文件长什么样

一个插件一份，文件名是 `catalog/plugins/<slug>.json`（`slug` 由 id 推出：`owner/repo` →
`owner__repo`，全小写，非法字符换成 `-`）。下面是 `catalog/plugins/nagi-ovo__dsh-ads.json`
的实例（人工核对留下的实测记录整段写在 `notes` 里，这里为便于阅读做了截断，其它值原样）：

```json
{
  "schemaVersion": 1,
  "id": "Nagi-ovo/dsh-ads",
  "slug": "nagi-ovo__dsh-ads",
 "package": "@dsh-external/dsh-ads",
  "name": "@dsh-external/dsh-ads",
  "title": "怀旧广告层（整活插件）",
  "summary": "纯整活：给界面套上 2005 年中文互联网风格的广告层，配假弹窗、抽奖转盘与奖励式推理广告，另有英文版恶搞文案。",
  "tags": ["界面美化", "整活", "主题"],
  "version": "0.1.0",
  "versionSource": "npm",
  "versionCheckedAt": "2026-09-17T15:55:14.674Z",
  "latestRelease": null,
  "author": "Nagi-ovo",
  "repo": "https://github.com/Nagi-ovo/dsh-ads",
  "homepage": null,
  "license": "BSD-3-Clause",
  "stars": null,
  "forks": null,
  "pushedAt": null,
  "metricsCheckedAt": "2026-09-17T15:55:14.674Z",
  "origin": null,
  "peerRuntimePin": "@deepseek-ai/cordis ^4.0.1, @deepseek-ai/dsh-client-locale ^0.1.0-rc.6, @deepseek-ai/schemastery ^3.18.1, react ^18.2.0",
  "peerVerdict": "warn",
  "peerNote": "4 个 peer 里 3 个满足……（实测启动无致命错误，属 warn 档）",
  "coexistenceWarning": null,
  "notes": "1. 它是**带客户端半**的插件（dsh.client.platform=web，inject 声明 @deepseek-ai/dsh-client-runtime 与 dsh-client-locale）……5. 许可 BSD-3-Clause，与其它插件不冲突。\n\n── 实测记录 ──\n隔离环境：DSH_HOME=…（一次性目录，与生产 ~/.dsh 完全分离）……① 安装 exit 0……⑤ 真实启动仅一行 dsh web 地址，无致命错误。\n\n核对结论：ok-with-notes（2026-09-17，dsh 0.1.6-alpha.1，node 24.14.0，pnpm 12.4.2，核对人 HaydenSmith1121）",

  "install": {
    "method": "github",
    "spec": "github:Nagi-ovo/dsh-ads",
    "commands": ["dsh plugin --profile web add github:Nagi-ovo/dsh-ads"],
    "url": null,
    "sha256": null,
    "bytes": null,
    "tarball": null,
    "dshVersion": "0.1.6-alpha.1",
    "needsConfig": false,
    "usageNeedsConfig": false,
    "risky": false,
    "riskyReasons": []
  },
  "source": {
    "kind": "manual",
    "url": "https://2bingling.github.io/dsh-market/plugins.json",
    "firstSeenAt": "2026-09-17T15:55:14.674Z",
```

> 字段顺序是**固定**的（由 `scripts/lib/catalog-format.mjs` 的 `serializeRecord` 决定）。
> 这不是洁癖：顺序不固定，7000 个文件每天都会显示为「已修改」，真正的变更会被噪音淹掉。

## 三、字段表：含义与谁写

「谁写」一列的含义：**采集**＝`scripts/sync-catalog.mjs` 联网采到就写、采不到就留 `null`；
**覆盖层**＝只能由人写在 `catalog/overrides/*.json` 里（采集器不会去改它）；
**反推**＝脚本从产物或源码算出来；**传承**＝本轮来源缺失时沿用上一轮配置文件里的值。

### 3.1 身份与展示

| 字段 | 类型 | 含义 | 谁写 |
|---|---|---|---|
| `schemaVersion` | number | 配置文件格式版本，当前 `1`。加字段不动它，改语义才动 | 脚本 |
| `id` | string | 插件 id：`owner/repo` 或包名 | 采集 / 覆盖层 |
| `slug` | string | 文件名主干，由 `id` 推出（`slugify`）：全小写、`/`→`__`、其余非法字符→`-`、截断到 120 字符 | 脚本 |
| `package` | string \| null | 包名（npm 包名或包本名）。**只有真包名才算「同一个插件」**，没有就如实写 `null`，绝不拿仓库名顶替 | 采集 / 覆盖层 |
| `name` | string \| null | 展示名，缺省回落到 `package` | 采集 / 覆盖层 |
| `title` | string | 展示标题。缺省依次回落到 `package` / `name` / `id` | 采集 / 覆盖层 |
| `summary` | string | 简介，最长 1200 字 | 采集 / 覆盖层 |
| `tags` | string[] | 标签，去重后最多 24 个（索引里只带前 12 个） | 采集 / 覆盖层 |

### 3.2 版本与收藏量

| 字段 | 类型 | 含义 | 谁写 |
|---|---|---|---|
| `version` | string \| null | 版本号。**解析不出来就是 `null`，绝不用别处的值凑一个看起来像版本的字符串** | 采集（覆盖层条目写死在 overrides 里） |
| `versionSource` | string | 版本号从哪来：`npm` / `github-release` / `github-tag` / `package.json` / `none` | 采集 |
| `versionCheckedAt` | ISO string \| null | 上一次「版本**真的**变了」的时刻（内容没变就不推进） | 脚本 |
| `latestRelease` | object \| null | GitHub release 事实：`{ tag, publishedAt, url }`。只有用 release 定版本时才有值 | 采集 |
| `stars` | number \| null | **收藏量 = GitHub star 数**（不是界面上的「点赞 / 收藏」，那是本地点标记）。以 GitHub 为准，公开索引兜底 | 采集 |
| `forks` | number \| null | fork 数 | 采集 |
| `pushedAt` | ISO string \| null | 上游仓库最后 push 时间 | 采集 |
| `metricsCheckedAt` | ISO string \| null | 上一次「收藏量 / push 时间**真的**变了」的时刻 | 脚本 |
| `author` | string \| null | 原作者。查不到就是 `null` —— **不代表没有，代表没核实到** | 采集 / 覆盖层 |
| `repo` | string \| null | 上游仓库地址（`https://github.com/owner/repo`） | 采集 / 覆盖层 |
| `homepage` | string \| null | 上游主页 | 采集 |
| `license` | string \| null | 许可标识（如 `MIT`、`BSD-3-Clause`、`NOASSERTION`） | 采集 |

### 3.3 兼容性与人工结论（只有人工核对过的条目才有）

| 字段 | 类型 | 含义 | 谁写 |
|---|---|---|---|
| `origin` | string \| null | 来源标记（自研插件为 `self`，派生包另有说明） | 覆盖层 |
| `peerRuntimePin` | string \| null | 该包对 `@deepseek-ai/*` / cordis / react 的 peer 约束原文 | 覆盖层 |
| `peerVerdict` | string \| null | peer 结论：`ok`（无约束或范围明确包含）/ `warn`（会打警告但实测可用）/ `critical`（版本不匹配会让整棵树挂） | 覆盖层 |
| `peerNote` | string \| null | 为什么是这个结论：实测还是推断、代价是什么 | 覆盖层 |
| `coexistenceWarning` | string \| null | 已知共存冲突（例如 `dsh-opencode-go` ↔ `dsh-opencode-go-plus`） | 覆盖层 |
| `notes` | string \| null | 维护者备注：副作用面、使用前提、审核时发现的坑 | 覆盖层 |
| `sha256Note` | string \| null | 自引用条目的说明：市场插件指向自己的 tarball，sha256 无法自包含进目录，权威值在同目录的 `.tgz.sha256` 边车文件里 | 反推 |

> 采集器**不会**替自动采集来的条目编造这些字段：拿不到就是 `null`。
> 「这个插件对我们这一版可用吗」这种结论只能来自真机实测或人工审核。

### 3.4 安装方式（`install`）

| 字段 | 类型 | 含义 |
|---|---|---|
| `method` | string | `tarball` / `npm` / `github` / `skills` / `manual` 之一（枚举见 `scripts/lib/catalog-format.mjs`） |
| `spec` | string \| null | `github:` 规格或 npm 包名。`tarball` / `manual` 通常为 `null` |
| `commands` | string[] | 展示用的命令（最多 6 条）。市场面板「手动安装」用的就是它 |
| `url` | string \| null | `tarball` 的下载地址（集合仓库或本仓库的 raw 地址） |
| `sha256` | string \| null | `tarball` 的校验和；自引用条目为 `null`，理由见 `sha256Note` |
| `bytes` | number \| null | `tarball` 的字节数 |
| `tarball` | string \| null | `tarball` 的仓库相对路径（本机有仓库副本时可离线直装） |
| `dshVersion` | string \| null | 这份产物适配的 **dsh 运行时版本**（不是插件版本） |
| `needsConfig` | boolean | 装完是否**必须**配置才能用（缺凭据 / 缺 API Key） |
| `usageNeedsConfig` | boolean | 能不能装、但**要用某个功能**时才需要配置 |
| `risky` | boolean | 是否有值得提示的风险信号（供应链 / 副作用面） |
| `riskyReasons` | string[] | 风险原因（最多 8 条），界面上逐条展示 |

**谁写**：自动采集条目的 `method` / `spec` / `commands` / `needsConfig` / `usageNeedsConfig` /
`risky` / `riskyReasons` 从公开索引里**干净的安装命令**推导；`tarball` 那一套由集合清单提供；
人工核对过的条目的 `spec` 与几个布尔量由人写在覆盖层里。

**自洽性检查**（脚本每次都会做，不通过就降级）：

| 声明 | 缺什么就降级成 `manual` |
|---|---|
| `github` | `spec` 不是 `github:` 开头 |
| `npm` | `spec` 不是合法 npm 包名 |
| `tarball` | 没有 `url` |

> 降级成 `manual` 的含义是「市场没有可自动执行的安装路径」：安装方案页会把上游说明原样列出来，
> 而不是让 pnpm 在装到一半时抛一个看不懂的错。它**不是**「不允许装」。

### 3.5 溯源（`source`）

| 字段 | 类型 | 含义 |
|---|---|---|
| `source.kind` | string | `public-index`（来自公开索引）/ `collection`（来自集合仓库清单）/ `self`（市场插件自己）/ `manual`（人工核对过的覆盖层） |
| `source.url` | string \| null | 这一条是从哪来的（索引地址、集合仓库地址或覆盖层 raw 地址） |
| `source.firstSeenAt` | ISO string \| null | **首次**被发现的时间。一旦写入，后续每轮都传承，不会因为上游改了简介就重置 |
| `source.lastSyncedAt` | ISO string \| null | 上一次内容**真的**变了的时刻 |

> ★ **0.5.0 删掉了 `tier` 与 `review` 两个字段。** 以前的 `review` 装的是人工审核证据
> （审核人 / 日期 / 环境 / 结论）；现在这些内容被拍平进条目的 `notes` 里
> —— 记录保留，但它**不再让条目升级成一个层级**。写法见
> [`catalog/overrides/curated.json`](../catalog/overrides/curated.json) 顶部的 `_comment`。

## 四、目录不分级（0.5.0）

以前这里列的是 `tier` 的三个取值（`verified` / `reviewed` / `community`）。
**这套分级已经删除**（0.5.0），理由见 [README 的「不分级的目录」](../README.md#tiers)：

- 分类回答的是「维护者该不该为这个插件背书」；
- 用户要回答的是「这个插件怎么装到我这儿」—— 0.6.0 起市场不判定任何插件能不能装，
  只把知道的事实（`notes`）如实列出来，自动还是手动由他自己在安装方案页选。

所以现在：

- 配置文件里**没有 `tier` 字段**，索引里也没有；`counts` 只有一个 `total`。
- 界面只有一个列表，没有层级页签、没有层级筛选、卡片上没有层级角标。
- 「装的是谁的字节」这件事仍然如实区分（`install.method === 'tarball'` 表示字节由本仓库托管），
  但它**不出现在任何判定里** —— 只影响静态探测能看多深：托管字节能逐字节看清候选包声明了什么，
  npm / GitHub 规格只能对上游仓库做静态探测。
- 排序：无关键词时按 star 数；关键词检索时按相关度 + star 数。层级加权已经删掉。

## 五、`catalog/index.json` 里的条目

列表页只读索引，所以索引里只放**展示与筛选**需要的字段 —— 完整字段见
`scripts/lib/catalog-format.mjs` 的 `indexEntry()`：

```none
slug / id / package / name / title / summary / tags(≤12)
version / versionSource / stars / repo / homepage / license / author / pushedAt
installMethod / installSpec / needsConfig / usageNeedsConfig / risky
peerVerdict / origin
```

索引还带几个头部字段：`schemaVersion`、`generatedAt`（**上游公开索引**的生成时间，
不是本仓库的生成时间）、`sourceIndex`（上游索引地址 / 生成时间 / 抓取时间 / 条数），
以及 `counts`（只有一个 `total` —— 条数必须等于 `catalog/plugins/` 下的配置文件数，CI 直接断言）。

## 六、加一个新插件 / 改一份配置

| 你想做的事 | 正确做法 |
|---|---|
| **自研插件发新版** | 在**集合仓库**里做：放新 tarball → 改 `plugins/<id>/plugin.json` → `node scripts/build-manifest.mjs`。本仓库不用动，下一次每日采集会自动跟上 |
| **给第三方插件补上实测记录** | `node scripts/market-review.mjs <owner/repo \| npm 包名 \| 插件 id>` 产出草稿 → 真机隔离环境实测 → 填 `notes` / `evidence` / `peer*` → 写进 `catalog/overrides/curated.json` → `node scripts/sync-catalog.mjs`。注意这是**补事实**，不是给它打一个「已审核」的标签 |
| **修正某个插件的版本 / star / 安装方法** | 一般**不要手改**配置文件：那是采集结果。先确认采集逻辑（`scripts/sync-catalog.mjs` + `scripts/lib/version-resolve.mjs`）是不是漏了什么；上游事实变了就等下一轮，或本地跑一次采集 |
| **下架某个插件** | 来自公开索引的条目：它从索引消失后会被自动删除（仅限 `source.kind=public-index`）。其余来源（市场自己 / 集合仓库 / 人工核对过的）**不会被自动删**，需要人工处理 |

来源标注义务（查不到作者 / 上游时怎么写「未注明」）见
[`CONTRIBUTING.md` 第二节](../CONTRIBUTING.md#sources)。
