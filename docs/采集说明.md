# 采集说明

**[← 回到首页](../README.md)**

采集器只有一个：[`scripts/collect.mjs`](../scripts/collect.mjs)。
它是**唯一**会写 `catalog/` 的脚本。

---

## 一、跑法

```bash
node scripts/collect.mjs                 # 联网采集（CI 每 6 小时跑的就是它）
node scripts/collect.mjs --check         # 只读校验：不联网、不写盘
node scripts/collect.mjs --offline       # 用 .cache/ 里上一轮的原始数据重跑归一化
node scripts/collect.mjs --only a/b      # 只处理一个仓库，其余记录原样继承
node scripts/collect.mjs --limit 200     # 只保留 star 最高的 N 条（试跑，不写盘）
node scripts/collect.mjs --pages 5       # 每个查询最多翻 5 页（默认 3 页 = 300 条）
node scripts/collect.mjs --quiet         # 只报错，不打印过程
```

| 路径 | 联网 | 写盘 | 能力边界 |
|---|---|---|---|
| 无参数 | ✅ | ✅ | 唯一会发现新项目、更新 star 数与描述的一条路 |
| `--check` | ❌ | ❌ | 核对索引自洽 + 快照是稳定投影。**不回答「上游是不是发了新版」** |
| `--offline` | ❌ | ✅ | 用缓存里的原始数据重跑一遍归一化；用来验证「改了合并逻辑会发生什么」 |

> ★ `--check` 的只读性是**有测试盯着**的（`test/data.test.mjs`）。
> 上一代脚本出过一次真事故：`--check` 的早退分支被写进一个不再被调用的函数里，
> 入口直接走到了联网采集那条路，把 7482 个文件删了然后 `exit 0`。
> 所以现在跑完校验会断言「工作区一个字节都没变」。

## 二、三路来源

| 来源 | 标识 | 优先级 | 拿得到什么 |
|---|---|---|---|
| **GitHub 搜索** | `github-search` | 3（最高） | 直读仓库：描述、star、fork、语言、topic、许可、主页、最近推送、是否归档 |
| **手工收录** | `seed` | 2 | 你写进 `catalog/seed.json` 的仓库；联网时去 GitHub 补齐元数据 |
| **公开索引** | `public-index` | 1（最低） | 第三方维护的 DSH 插件清单，覆盖面最广 |

### 为什么主力是 REST 搜索，而不是上一版的批量 GraphQL

上一版逐仓库取字段（star / release / tag / package.json），一轮要花掉几百到几千点配额。
这一版要的东西少得多，而 GitHub 的**搜索接口一次就返回 100 个完整仓库对象** ——
描述、作者、star 数全在里面。同样的信息量，请求数从「每仓库一次查询节点」
降到「每 100 个仓库一次 HTTP」。

代价是搜索接口有自己的限流（认证后 30 次/分钟，每次最多 100 条、
每个查询最多 1000 条结果）。所以：

| 做法 | 原因 |
|---|---|
| 用**多个窄查询**（8 个 topic / 关键词切面）而不是一个宽查询翻到底 | 每个查询 1000 条就封顶了；多个切面各取前几页，覆盖面更广，而且每个切面天然按 star 降序拿到头部 |
| 每个查询默认只翻 3 页 | 8 × 3 = 24 次请求 ≈ 1 分钟跑完，远在配额之内 |
| 命中限流就等 `retry-after` 再试，最多 4 次 | 采集宁可少采一轮，也不能挂死在 CI 里 |
| 相关性过滤只作用于搜索结果 | 公开索引与 seed 是别人/自己明确为 DSH 收的，不拿启发式二次判断 —— 那会把「我确定它是插件」变成「我觉得它是」 |

### 合并规则

同一个仓库被多路发现时，**字段级**取舍（`scripts/lib/catalog-format.mjs` 的 `mergeRecords`）：

- 非空值：来源排名高的赢
- `topics`：取并集
- `sources`：取并集 —— 「这条是从哪儿知道的」本身就是要展示的事实
- `firstSeenAt`：取最早的一次
- `lastSyncedAt`：取最新的一次

## 三、三条硬规矩

### ① 内容没变就不动时间戳

一条记录里有两个时间戳：`firstSeenAt`（第一次看到它）与 `lastSyncedAt`（最后一次看到它）。
判断「有没有变」时只比较**内容投影**（`recordContent`：去掉这两个字段的其余字段）。

顶层的 `generatedAt` 同理：**整份索引的内容**（计数 + 来源 + 全部记录的内容投影）
没有任何变化时，`generatedAt` 保持原值，于是生成的文件逐字节相同，
git 里自然没有东西可提交。

### ② 没看过就不删

某个来源这一轮失败了（限流、断网、接口改了），由它发现、这一轮又没被别的来源看到的记录
**原样保留**。判断依据是「产生它的来源这一轮成功了吗」：

```
sourcesFailed = 记录的 sources 里有任何一个这一轮失败了
```

`sourcesFailed` 为真 → 保留；否则再看它是不是 90 天没被任何来源看到过 —— 是才清理。

> 把「没查到」当成「不存在」，是这类采集器最容易犯、也最难发现的错误：
> 一次限流就能静默删掉几百条记录，而界面上只是「项目变少了」。

### ③ 输出逐字节确定

| 措施 | 在哪 |
|---|---|
| 排序规则固定（star 降序 → id 升序），且**只实现一次** | `sortRecords` |
| 记录的键顺序固定 | `normalizeRecord` |
| `topics` 去重 + 小写 + 排序 | `normalizeRecord` |
| 时间只写 ISO 格式 | `isoDate` |
| 序列化「一条记录一行」 | `serializeIndex` |

同输入必得同字节，所以 CI 里「采了一轮但没变化」不会产生任何 diff。

## 四、产物

| 文件 | 是什么 | 谁在读 |
|---|---|---|
| `catalog/index.json` | 全部记录（唯一事实来源） | 面板运行时会去仓库 raw 拉这一份 |
| `catalog/snapshot.json` | 上面那份的**稳定投影**：star 最高的 400 条，登记性字段清空 | 打进插件包，没网时当兜底 |

`snapshot.json` 进包前会把 `firstSeenAt` / `lastSyncedAt` 清成 `null`，
并且 `generatedAt` 也写成 `null`。理由只有一个但代价很大：

> 快照随插件包一起安装。如果它随索引的日常刷洗而变，那么每 6 小时一次的采集
> 都会改到包，而包的内容变了、版本号没变 —— 装过的人不会收到任何更新，
> git 里却天天多一个 diff。清空之后，只有**实质内容**（新项目出现、star 数变化、
> 描述改写）才会动到包。

## 五、本地缓存（`.cache/`）

不进版本库（见 `.gitignore`）。`--offline` 读的就是它。

| 文件 | 内容 |
|---|---|
| `public-index.json` | 公开索引的瘦身版（只留采集要用的字段，原始 ~22MB 太大） |
| `search-<hash>.json` | 每个查询上一轮的原始结果 |

删掉 `.cache/` 是安全的：下一次联网采集会重新填。
