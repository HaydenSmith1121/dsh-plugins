# 跨版本适配

**[← 回到首页](../README.md)**

**目标：同一个包，同时活在 dsh 0.1.5 / 0.1.6 / 0.1.7-rc.2（含官方桌面版）上。**

机器可读的矩阵在 [`compatibility.json`](../compatibility.json)。
下面说清楚「为什么这么设计」与「踩过哪些坑」。

---

## 一、五条设计约定

### ① 一个 peerDependency 都不写

dsh 0.1.7 起，**在导入插件之前**会核对它 `peerDependencies` 里的
`@deepseek-ai/dsh` 与 `@deepseek-ai/dsh-*` 是否与当前运行时版本一致。
不一致就直接不让导入。

写了 peer，就等于把自己钉死在某一个 dsh 版本上。所以本包：

```json
// package.json 里没有这几个键
"dependencies": …,
"peerDependencies": …,
"optionalDependencies": …
```

`test/manifest.test.mjs` 有一条测试专门断言它们**不存在** ——
将来有人为了图方便加一个依赖，会先红。

### ② 不声明 `engines.dsh`

当前版本的 dsh **不强制检查** `dsh.manifestVersion` 与 `engines.dsh`
（官方文档原话：「Current installers and loaders do not enforce …」）。
但那是「现在不查」，不是「永远不会查」。声明一个 `>=0.1.7` 只会让旧版本装不上，
换不来任何好处。

只保留一个宽松的 `engines.node`。

### ③ 服务器半零依赖

`src/server/` 里只 `import` Node 内置模块（`node:fs` / `node:path` / `node:zlib` …）。
理由有两层：

- 每多一个依赖，就多一分 pnpm 解析失败 / `ERR_PNPM_IGNORED_BUILDS` / 离线不可用的风险；
- 这个插件的意义是「只读地展示一份搜集结果」，没有任何理由为此引入一个依赖树。

`test/manifest.test.mjs` 会扫描 `src/server/` 下所有 `import` 语句，
出现裸包名就失败。

### ④ 只用各版本都在的 API

| 位置 | 用的东西 | 从哪个版本起有 |
|---|---|---|
| 服务器半 | `ctx.effect(cleanupFn)` | cordis 核心 |
| 服务器半 | `webServer.register({ kind, path, handler })` | dsh web 早期就有 |
| 客户端半 | `window.__ModuleLoader__.load({ id, factory })` | 客户端模块系统 |
| 客户端半 | `slots.inject(slot, cb)` / `slots.register(options, renderer)` | slot 系统 |
| 客户端半 | `require('react')` | baseline seed word |

**刻意不用**（虽然更新版本上有）：

| 不用 | 为什么 |
|---|---|
| `webServer.registerFallback` / `registerUpgrade` | 0.1.7 才有 |
| `pluginPackages` / `pluginInventory` / `profileContext` | 0.1.7 才有，且形状还在动 |
| `@deepseek-ai/dsh-client-ui-primitives` 等客户端包 | 官方插件编写指南自己写着「不要 require 它们，自己写控件」 |
| `dsh.client.immediately` | 0.1.7 新增；写了在旧版本上是未知键，不写在新版本上只是延迟加载 —— 不写更安全 |

### ⑤ 能力探测代替版本判断

真正决定「能不能干活」的是 `webServer.register` 在不在、`ctx.effect` 在不在，
**不是版本号字符串**。所以 `src/server/compat.js` 的 `probeHost(ctx)` 探测能力，
面板的「关于」里如实显示：

```
插件 API    webServer.register ✓
宿主服务    webServer、storage
```

某天某个版本把这个 API 改了名字，用户看到的是这一行变成 ✗（而不是白屏），
同时 harness 本身不受影响。

## 二、`compatibility.json` 不构成闸门

它只回答一个问题：**「这个版本有没有人真的跑过」**。

| status | 含义 |
|---|---|
| `supported` | 真机上装过、面板打开过、数据出来了 |
| `expected` | 按 API 形状推断可用，但没有人实测过（会写清楚推断依据） |
| `broken` | 实测不可用（会写清楚坏在哪一步） |

**版本不在表里、或者标着 `expected`，插件照样全功能可用。**
面板上会显示一个「未实测」的标签，仅此而已。

### 当前实测结果（2026-09-27）

| dsh 版本 | 通道 | 状态 | 实测到了哪一步 |
|---|---|---|---|
| `0.1.7-rc.2` | 官方桌面版 | ✅ supported | 从桌面版装 → 侧栏图标 → 面板打开 → 9423 条 → 搜索 / 复制可用 |
| `0.1.6-alpha.2` | 命令行 | ✅ supported | 装上 → `status`/`index` 两个 RPC 均 200 → 启动图有客户端半 → 客户端半本体取回 44,212 字节 |
| `0.1.5-rc.3` | 命令行 | ✅ supported | 同上；且该线宿主服务更少（无 `pluginPackages`/`profileContext`），能力探测如实报出，功能不受影响 |
| `0.1.6-alpha.1` | 命令行 | ⛔ broken | runtime 自己装不起来（上游发版问题，与本插件无关，见第三节 ⑥） |
| `0.1.5-rc.1` / `0.1.5-rc.2` | 命令行 | ⚠️ expected | 未单独实测；同线 rc.3 已通过 |

> ★ `0.1.5-rc.3` 那一行值得单独看一眼：它的宿主服务比 0.1.6 少了两个，
> 而插件**照常工作** —— 因为它只 `inject` 了 `webServer` 一个服务，
> 其余一切都走 `ctx.get(...)` 并判空。这就是「能力探测代替版本判断」的实际收益：
> 少一个服务不会让面板消失，只会让「关于」里少显示一行。

> 上一版（插件市场）在这件事上走过另一条路：它把 dsh 版本锁死在一个矩阵里，
> 不在矩阵里就拒绝安装。那条路的问题是它把一个**建议**做成了**闸门** ——
> 而实测下来，绝大多数「不在矩阵里」的版本其实工作得很好。

## 三、踩过的坑（都是实测记录）

### ① 仓库子目录装不了（1.0.0 重构的直接原因）

官方桌面版的安装规格解析器用这几个正则判断输入：

```
GIT_SHORTHAND          /^(?:github|gitlab|bitbucket|gist):/i
GIT_URL                /^git(?:\+[a-z]+)?:\/\/|^git@[^:]+:/i
HOSTED_REPOSITORY_URL  /^https?:\/\/[^/]+\/[^/]+\/[^/#]+(?:\.git)?(?:#.*)?$/i
TARBALL_SPEC           /\.(?:tgz|tar\.gz)(?:#.*)?$/i
```

`HOSTED_REPOSITORY_URL` 只允许 `host/owner/repo` 三段。
`https://github.com/a/b/sub` **不匹配**，报
「a URL must point at a git repository or a tarball」。
也没有 `gitpkg` 那种 `#path:subdir` 语法。

**结论**：插件的 `package.json` 必须在**仓库根**。
这就是 1.0.0 把插件从 `plugins-src/dsh-plugins-market/` 搬到根目录的原因，
也是 `test/manifest.test.mjs` 里那条「仓库根就是插件包」断言的由来。

### ② `dsh.client` 有严格类型校验

解析器会对字段做类型检查，类型不对直接抛错：

| 字段 | 要求 |
|---|---|
| `dsh.client` 本身 | 必须是对象（`has a non-object dsh.client declaration`） |
| `dsh.client.platform` | 必须是字符串 |
| `dsh.client.immediately` | **若出现**必须是布尔值 |
| `dsh.client.inject` / `external` | 字符串数组 |
| `exports["./client"]` | 声明了 `dsh.client` 就必须有，否则报 `declares dsh.client but exports no "./client" bundle` |

### ③ `dsh.bundle.patch` 可以是路径或路径数组

校验器抛出的错误原文是 `dsh.bundle.patch must be a file path or a list of file paths`。
本包用单个字符串。

### ④ 客户端半是 classic script

宿主用 `<script async src=…>` 加载它（没有 `type="module"`）。
写了 `import` / `export` / 顶层 `await` 就是 SyntaxError，
表现是控制台一句 `bundle … loaded without registering "id"`，以及**整个面板不出来**。
`test/bundle.test.mjs` 会静态检查这几条。

### ⑤ 少了 `exports["./client"]` 或 id 写错，症状一样

都是「装上了但界面上没有」，都不会有任何编译期报错。所以这两条也在测试里。

### ⑥ 装「非该线最新」的 dsh 版本会解析到更新的同线库

实测：`npm i @deepseek-ai/dsh@0.1.6-alpha.1` 之后，`dsh --version` 自己都起不来 ——

```
SyntaxError: The requested module '@deepseek-ai/dsh-app-boot'
does not provide an export named 'watchUserPatches'
```

原因是 `dsh@0.1.6-alpha.1` 的依赖写成 `^0.1.6-alpha.1`，而 `0.1.6-alpha.2` 已经发布，
于是那批 `@deepseek-ai/dsh-*` 全被解析成 alpha.2，而 alpha.1 的 CLI 用了 alpha.2
已经删掉的导出。**这与任何插件都无关** —— 装不上，是因为 runtime 自己装不上。

> 结论：装**同一线的最新版**（0.1.6-alpha.2、0.1.5-rc.3）。这条也写进了
> `compatibility.json` 的 `knownTraps`。

### ⑦ 想确认客户端半到底有没有被登记，看**启动图**

「装上了但界面上没有」有两种完全不同的成因：服务器半没加载（面板打不开），
或者客户端半没登记（侧栏没有图标）。后者不会报错，只会静默缺席。

判断方法很直接：页面 HTML 里带着一份启动图，客户端半在里面就是一行 ——

```json
{"id":"dsh-plugins-market","url":"/plugins/??dsh-plugins-market/client.js&rev=5f67cc7d4edfed05-53","inject":[]}
```

拿到这个 URL 直接取一次，应当是 `__ModuleLoader__.load(...)` 的客户端半本体：

```bash
curl -s "http://127.0.0.1:<port><那个 url>" | head -c 200
# 期望看到 window.__ModuleLoader__.load({ id: "dsh-plugins-market", ...
```

★ 页面 HTML 通常需要 token（`dsh web` 启动时会打印形如
`http://127.0.0.1:<port>/?token=...` 的地址），而插件自己的 API 路由**不需要** ——
所以「API 通、页面取不到」是正常的，不要据此判断插件坏了。

## 四、怎么给新版本补一条实测结论

下面是 1.0.0 实测 0.1.6-alpha.2 / 0.1.5-rc.3 时用的完整流程。它**不碰你日常用的
`~/.dsh`**：全程用独立的 `DSH_HOME` 与独立端口。

```bash
# ① 装一套隔离的 dsh + pnpm 到自己的目录里（不要 -g，免得动到日常那套）
BASE=/path/to/scratch/_verify
npm i --prefix "$BASE" --no-audit --no-fund "@deepseek-ai/dsh@0.1.6-alpha.2" pnpm@10

# ② 用它自己的 node 跑它自己的 bin.js，并把 DSH_HOME 指到隔离目录
DSH="$BASE/node_modules/@deepseek-ai/dsh/lib/bin.js"
export DSH_HOME="$BASE/home"
export PATH="$BASE/node_modules/.bin:$PATH"

node "$DSH" --version                            # 确认版本
node "$DSH" plugin --profile web add /path/to/dsh-plugins   # 装本插件（本地路径）
node "$DSH" web --port 3091 --no-open &          # 起一个隔离实例

# ③ 验宿主半：插件自己的路由不需要 token
curl -s -X POST http://127.0.0.1:3091/dsh-plugins-market/api \
     -H 'content-type: application/json' \
     -d '{"method":"status"}'

# ④ 验客户端半：从启动图里找 /plugins/??dsh-plugins-market/client.js 那一行，
#    取回来确认它是 __ModuleLoader__.load 的客户端半本体（见上面第 ⑦ 条）
```

然后确认面板能打开、列表有数据、搜索有结果、复制安装地址可用，最后把结论写进
[`compatibility.json`](../compatibility.json)：

```json
{
  "dshVersion": "0.1.8",
  "channel": "desktop",
  "status": "supported",
  "verifiedAt": "2026-10-01",
  "verifiedOn": {
    "os": "Windows",
    "node": "24.18.0",
    "result": "装上后侧栏出现「插件搜集」，索引载入 9423 条，搜索与复制正常。"
  }
}
```

> **只写你真的跑过的。** 没实测就写 `expected` 并说明推断依据；跑不起来就写
> `broken` 并写清楚坏在哪一步（0.1.6-alpha.1 那一条就是这么记的）。
> 写一个假的 `supported` 比空着更糟：下一个人会拿它当依据。
