## 一、兼容策略

### 为什么按 dsh 版本分层

插件对 dsh 运行时（`@deepseek-ai/*`）的依赖有两种写法，都会导致「只适配有限版本」：

- **精确 pin**（`dsh-opencode-go-plus` 的 `0.1.6-alpha.1`）—— 换版本即崩
- **窄范围**（`dsh-workbuddy-connect` 的 `^0.1.5-rc.1`）—— 换版本可能只是警告，也可能是隐患

所以同一个插件在 dsh 不同版本下往往**需要不同的构建产物**。
目录结构 `plugins/<包名>/<dsh 版本>/` 就是为此预留的：
新 dsh 版本发布后，**增量补一套目录即可，不影响已有的**。
（这套目录约定现在主要落在插件集合仓库里；本仓库只剩市场插件自己一个产物目录。）

详见[目录结构](./目录结构.md)与[版本兼容矩阵](./版本兼容矩阵.md)。

### 只剩「诊断机器」这一类，而且它不拦插件

0.6.0 删掉了「装前兼容性检查」整层（`src/server/gate.js` 已删除）：市场**不判定任何插件能不能装** ——
所有插件都可装，用户在安装方案页自己选**自动安装**（市场在服务端执行命令，界面上不弹命令窗口，
用进度页展示阶段 / 已耗时 / 预计剩余，可随时中止，失败自动回滚）还是**手动安装**
（把命令给你，自己在终端执行 —— 下载 tarball + sha256 校验 + `dsh plugin add` + 三层校验 + 重启）。
两条路同时摆在最上面，默认自动，自动不可用时落到手动。

★ 为什么删：那套判定只能看静态探测结果，看不到真实发布产物、运行时行为与依赖闭包，
而它给出的「不安全」结论会被当成「装不了」，把本来能用的插件挡在门外。现在的分工是：
市场把知道的事实（`notes`：没声明 `dsh.bundle.patch`、声明了 patch 但包里没有这个文件、
peer 精确 pin 到比本机更新的版本、与已装的插件不能共存、需要配置才能用、上游带安装脚本）
**如实列出来**，由用户决定。

剩下的检查里，只有**诊断机器**这一类还会中止安装：

| 检查 | 位置 | 现在的作用 |
|---|---|---|
| 环境预检 | `scripts/preflight.mjs`（只读） | 报出 Node / pnpm / dsh 版本不对、pnpm 装错 Node —— 诊断的是机器，不是插件 |
| profile 完整性体检 | 自动安装前自动跑（`src/server/diagnose.js` 的 `checkProfile()`） | 断链的 `file:` 依赖、`pnpm-workspace.yaml` 不变量被破坏时**中止这次安装** —— 这种机器状态下装了也必然失败，与装哪个插件无关 |
| 四步校验 | `scripts/verify.mjs` | 装完再跑：版本 / 依赖层 / 装配层 / 真实启动 |
| 配置文件即事实 | 市场面板读 `catalog/plugins/<slug>.json` | 解析不出可自动执行的安装规格（`resolveInstallSpec()` 返回 `null`）就退回手动说明 —— 不拿显示名去猜一个包名装，也不是「不允许装」 |
| 收录快照 | 集合仓库 `snapshots/` + `manifest.json` | 上游更新后装不回当初验证过的那一版（第三方插件不分发字节，由上游保证） |

> ★ 一句话记住这个区别：**诊断机器的问题会拦住安装；判定插件的好坏不再拦任何东西。**

## 二、注意事项

### ★ pnpm 必须装在「dsh 所在的那个 Node」上

这是新机安装**最容易踩、也最难自查**的一个坑。多 Node 环境（nvm、便携版 Node 并存）
下，直接跑 `npm i -g pnpm` 很可能装到了**另一个** Node 上。结果是：

```none
'pnpm' 不是内部或外部命令，也不是可运行的程序或批处理文件。
dsh: pnpm failed in profile directory C:\Users\...\.dsh\profiles\web
```

连 `dsh plugin --profile web list` 都会这样报 —— 因为 `list` 同样转发给 pnpm。

**正确做法**：先确认 dsh 在哪，再用**那个目录里的 npm** 装 pnpm。

```powershell
# 1) 找 dsh 的安装位置
Get-Command dsh | Select-Object Source
#    假设输出 C:\Users\你\AppData\Roaming\npm\dsh.cmd

# 2) 用同一个目录下的 npm 装 pnpm
& "C:\Users\你\AppData\Roaming\npm\npm.cmd" install -g pnpm
```

```bash
# macOS / Linux 同理：where/which dsh 找到 prefix，再用该 prefix 里的 npm
which dsh          # 例：/usr/local/bin/dsh  → prefix 是 /usr/local
/usr/local/bin/npm install -g pnpm
```

`node scripts/preflight.mjs` 会自动做这项比对，并在不一致时直接给出该执行的命令。

### ★ tarball 所在目录不能删、不能挪

`dsh plugin add <tarball>` 生成的**不是**把包内容拷进去，而是 `file:` 形式的依赖：

```json
"dsh-plugins-market": "file:C:/Users/你/.dsh-plugins/plugins/dsh-plugins-market/0.1.6-alpha.1/dsh-plugins-market-0.4.0.tgz"
```

这个 `file:` 指向的路径**不能删除、不能移动**，否则以后任何 `pnpm install` /
`dsh plugin` 操作都会失败（找不到 tarball）。

自 0.4.0 起 tarball 只可能来自这三处，规则对它们**一视同仁**：

| 来源 | 路径 |
|---|---|
| 本仓库的 clone（市场插件） | `~/.dsh-plugins/plugins/dsh-plugins-market/<dsh 版本>/*.tgz` |
| 市场面板下载的缓存 | `$DSH_HOME/storages/dsh-plugins-market/tarballs/`（按 sha256 复用） |
| 你自己手动下载的 | 你放它的地方 —— **别放 `%TEMP%` 或会被清理的下载目录** |

- 已经装好的 profile 运行时**不需要** tarball（内容已在 `node_modules`），
  但重新安装 / 升级时会需要
- 引导脚本把仓库落地在 `~/.dsh-plugins`，**不要**安装完就把它删掉

**自检**：

```bash
grep -o 'file:[^"]*' ~/.dsh/profiles/web/package.json
# 逐条确认这些 tarball 路径真实存在
```

万一路径确实失效了（挪了仓库、清了缓存），正确做法是三步：**重新 add → 重跑 install → 跑校验**：

```bash
# 1) 直接重新 add 一遍（市场插件可从面板「修复 / 重装」，或按 README-安装说明.md 手动 add）
# 2) 重跑 pnpm install 让链接指向新位置
cd ~/.dsh/profiles/web && pnpm install
# 3) 真实启动校验
node scripts/verify.mjs
```

<a name="pitfalls-ignored-builds"></a>

### ★ 特别当心：`ERR_PNPM_IGNORED_BUILDS` 的假象

```none
Error: ERR_PNPM_IGNORED_BUILDS
  × adding a new package
  ╰─▶ Ignored build scripts: @google/genai@1.52.0, protobufjs@7.6.6
  help: Run "pnpm approve-builds" to pick which dependencies should be allowed to run scripts.
dsh: pnpm failed in profile directory ...
```

看到这个报错，第一反应是「装失败了」。但实际状态是：

| 检查项 | 实际 |
|---|---|
| `node_modules/dsh-opencode-go-plus/` | ✅ **已存在**，依赖也全部链接完毕 |
| `package.json` 的 `dependencies` | ✅ **已写入** |
| `package.json` 的 `dsh.profile.bundles` | ❌ **没有追加** |

原因：dsh 的流程是「先跑 pnpm → 成功后才写 bundles」。pnpm 因「有未批准的构建脚本」
**以非 0 退出**，dsh 就提前 return 了。

**最终表现**：插件文件都在 `node_modules` 里，但 **GUI 里完全看不到它** ——
很容易误判成「装了但没生效」而去查前端。

> **规矩：只要 pnpm 退出码非 0，就当作「这条插件没装完」。**
> 别被 `node_modules` 里有文件骗到。

**修法**：预置 `allowBuilds`，然后**重跑同一条 `dsh plugin add`**
（幂等，会报 `Lockfile is up to date`）→ 退出码 0 → dsh 这才补上 bundles 条目。

在 `~/.dsh/profiles/web/pnpm-workspace.yaml` 里加上：

```yaml
allowBuilds:
  '@google/genai': false
  protobufjs: false
```

**为什么填 `false` 是安全的**：

| 包 | 声明了什么脚本 | 实际作用 | 需要跑吗 |
|---|---|---|---|
| `protobufjs` | `postinstall: node scripts/postinstall` | 只打印一句 protobufjs-cli 提示 | ❌ 纯装饰 |
| `@google/genai` | `prepare: node scripts/prepare.js` | `prepare` 对 registry / tarball 安装**本就不执行**（仅 git / 本地目录安装生效） | ❌ 不会跑 |

填 `false` 的含义是「**已知并同意忽略**」，不是「跳过构建」。

> ⚠️ **不要用 `strictDepBuilds: false` 一把梭** —— 那会把将来真正需要编译的依赖
> （native 模块等）也静默跳过。用 `allowBuilds` 逐个白名单更安全：
> 保留了严格模式，遇到新的未知构建脚本仍会报出来。
>
> ✅ 已实测：dsh **不会覆盖**这个文件，手写的 `allowBuilds` 能长期留存。
> 也无需 `pnpm approve-builds`（那是交互式的，不适合脚本化）。

### ★ 开发产物别混进生产 profile

改完插件重新打包后，**必须先 `remove` 再 `add`**：

```bash
dsh plugin --profile web remove <包名>
node scripts/dev-env.mjs install <插件 tarball 的绝对路径>
#   例（市场插件）：node scripts/dev-env.mjs install plugins/dsh-plugins-market/0.1.6-alpha.1/dsh-plugins-market-0.4.0.tgz
```

同一个 tarball 路径内容变了时，pnpm 会认为 lockfile 是新的、**跳过解包**
（`Lockfile is up to date, resolution step is skipped`），加 `--force` 也只重新链接、
不重新解包 —— 你会一直在跑旧代码。

### 隔离环境：`DSH_HOME`，不是 `--profile`

`--profile` 只隔离插件树，凭据 / 设置 / 会话仍共享。做插件开发请用
[`README-开发环境隔离.md`](../README-开发环境隔离.md) 里的隔离脚手架
（整个主目录独立），日常在用的 3080 与开发用的 3090 可以同时跑。

### ★ 最大也最常见的长期陷阱：静默降级

`npm i -g @deepseek-ai/dsh`（**不带版本**）装的是 `latest`。以后只要顺手跑一次
这样的升级，就会把 CLI **静默降回旧版本**，故障立刻复现，而且**没有任何提示**。
详见[版本兼容矩阵 § 两条必须记住的规矩](./版本兼容矩阵.md#two-rules)。

### 手动装插件时的两个提醒

- **顺序即 bundle 层级顺序**：现在插件是逐个点装 / 逐个 `add` 的，它们会被追加到 profile 已有的
  `dsh.profile.bundles` 之后；历史导出快照见 `profile-config/profile-bundles.yaml`
  （**市场分离前**的顺序，里面仍有已不在本仓库的 tarball 名字）。
- **`--dump-config` 通过 ≠ 能启动**：它只打配置树、不 import 任何模块，
  所以「缺具名导出」这类问题它完全查不出来；反过来，真实启动也查不出 bundles 顺序错。
  **两步都要做**，这也是 `scripts/verify.mjs` 第 ③④ 步同时存在的原因。

### 凭据与登录态不随包迁移

本仓库**有意不含** `.credentials.yaml`（API key 所在）：

- 各 provider 的 API key → 首次启动后在 GUI 设置里手填
- **trae 登录态** → 需在目标机重新登录
- `dsh-workbuddy-connect` 复用 **WorkBuddy 桌面端**的登录态，不另起 OAuth

<a name="read-only-check-incident"></a>

## 二·补、一次真实的「只读命令删了 7482 个文件」

记在这里是因为它的教训比事故本身有用。

**发生了什么**：`node scripts/sync-catalog.mjs --check` —— 一条被文档描述为「只校验、
不写盘、CI 用」的命令 —— 删掉了 `catalog/plugins/` 下 7482 个配置文件，写出了一份
只剩 14 条的索引，报告「目录校验通过」，然后 **exit 0**。

**为什么**：重构时把联网采集那段函数从 `main()` 改名成 `collect()`，入口改成
`await collect()`，但 `--check` / `--offline` 的**早退分支留在了 `main()` 里** ——
而 `main()` 已经不再被任何地方调用。于是：

```
--check  →  直接走联网采集
         →  本机 .cache 刚被清掉，公开索引拉不到，推演出的记录集只剩 14 条
         →  「配置文件数 == 期望记录数」这条判据判定 7482 个文件是**多余的**
         →  删掉它们，报告成功，退出码 0
```

**为什么没丢东西**：这 7496 个配置文件是**提交进版本库**的，不是「生成物」。
`git checkout -- catalog` 一个字节不少地全恢复了。这也是这套目录为什么值得
全部进 git，而不是靠「随时能重新生成」：重新生成依赖网络、依赖上游此刻的状态，
而「此刻的上游」和「当时的上游」不是同一个东西。

**怎么修的**（三条，缺一不可）：

1. **让「只读」成为结构，而不是一个 if**。入口 `main()` 只做三件事：读磁盘上已有的
   记录、按 flag 分流、把结果交给对应实现。它不再包含任何采集逻辑，也就不存在
   「早退分支被落下」的空间。`checkOnDisk()` 里**没有任何写操作**。
2. **`--check` 不再依赖网络缓存**。它原先走主流程，于是「CI 能不能过」取决于本机
   有没有 `.cache` —— 缓存一清就产生一条与工作区毫无关系的假警报。校验的本质是
   「磁盘上的东西自洽不自洽」，那就只读磁盘。
3. **加一条断言**。`verify.yml` 里跑完 `--check` 之后断言 `git diff` 为空。
   这类事故的教训就是：**注释挡不住它，断言可以。**

> 通用一点的结论：**任何「只读」命令，都要有一条「跑完之后工作区没变」的断言。**
> 光在文档和注释里写「本命令不写盘」是不够的 —— 它描述的是作者的意图，
> 不是程序的行为。

## 三、卸载 / 回滚

```bash
dsh plugin --profile web remove <包名>     # 例如: dsh plugin --profile web remove dsh-receipt
```

> 动手前建议先备份 `~/.dsh/profiles/web/` 下的这 3 个文件：
> `package.json`、`pnpm-workspace.yaml`、`cordis.patch.yml`。
> 出错时把它们还原即可整体回滚。

**市场面板起不来时**，用「已装」页里的**三层校验 / 真实启动校验 / 快照回滚 / 修复 profile**
（0.3.0 起不再有独立的「体检」页签，这些入口搬到了「已装」页，
备份目录是 `$DSH_HOME/storages/dsh-plugins-market/backups/`），或者直接跑一次校验看是哪一层出的问题：

```bash
node scripts/verify.mjs --profile web
```

### `dsh-opencode-go-plus` 与 `dsh-opencode-go` 不能共存

两者共用设置命名空间 `llm-opencode-go` 与 provider 路由 `opencode-go`，
四种组合都实测过（Windows / Node 24.14.0 / pnpm 12.4.2 / dsh 0.1.6-alpha.1）：

| 安装情况 | `dsh web` | 结果 |
|---|---|---|
| 只有 `dsh-opencode-go-plus` | ✅ 正常 | `opencode-go` 分组 **38** 条模型 |
| 只有 `dsh-opencode-go` | ✅ 正常 | `opencode-go` 分组 **37** 条（无 `union-alpha`） |
| 两者共存，基线在前 | ✅ 正常 | 基线服务 37 条；plus 记一条 warn 后**主动退场** |
| 两者共存，plus 在前 | ❌ **退出码 1** | 基线抛未捕获的 `DUPLICATE_DISCOVERY`，整树加载失败 |
| 两者共存，基线被 patch `disabled` | ✅ 正常 | plus 服务 **38** 条 |

第四行是**基线的缺陷**，本包无法阻止 —— 唯一办法就是别把两个装在一起。
**升级路径是「先卸后装」**（`dsh-opencode-go-plus` 的 tarball 在插件集合仓库里，
下载地址与 sha256 见那边的 `README.md`）：

```bash
dsh plugin --profile web remove dsh-opencode-go
dsh plugin --profile web add <下载后的 dsh-opencode-go-plus-0.3.0.tgz 绝对路径>
```

**怎么确认装对了：数模型数**。plus 是 **38** 条并含 `union-alpha`；基线是 37 条且没有它。
完整来历与改动清单见
[`README-安装说明.md` 第十节](../README-安装说明.md#ch10)。
