# 收录说明

**[← 回到首页](../README.md)**

> 本页说明「收录快照」是什么、为什么收录的不一定是最新版本、以及怎么校验。
> **收录目录本身**（逐条版本 / 作者 / 上游仓库 / sha256）在
> [`collection/README.md`](../collection/README.md)；
> **收录规则**（新增收录必须遵守）在 [`collection/SPEC.md`](../collection/SPEC.md)。

---

## 一、收录快照解决什么问题

插件市场装的是「**收录当时那一版**」。上游发新版后可能出现这些情况：

| 上游发生的动作 | 对用户的后果 |
|---|---|
| 撤回旧版本（unpublish） | 老用户重装时**装不回来** |
| 用同一版本号重新发布不同内容 | 装到的**和当初验证过的不是同一份** |
| 收紧 `peerDependencies` | 原本可用的 dsh 版本**突然装不上** |
| 改动包结构（挪 `lib/`、去掉 `cordis.patch.yml`） | 装上了但**GUI 里没有** |

这些都不是用户能预判的。`collection/` 就是为此存在的：
**把验证过的那个字节固定下来**，让它能被原样装回去。

---

## 二、⚠️ 收录的不一定是最新版本

**这是设计意图，不是缺陷。**

收录标准是「**在真机上验证过、装得上、跑得起来**」，**不是「追平上游」**。
上游最新版可能改了 peer 约束或包结构，反而装不上。
旧快照的价值恰恰在于：等上游发新版之后，**这一版还能原样装回去**。

| | 收录原则 | 上游发布节奏 |
|---|---|---|
| 目标 | 验证过的字节可复现 | 持续发新版 |
| 关注点 | 装得上、不崩 | 加功能、改结构 |

> 需要最新版时：先按 [`collection/SPEC.md`](../collection/SPEC.md) 真机验证，
> **再新增一套快照，不覆盖旧版**。

---

## 三、收录了什么

**运行时基线：`dsh 0.1.6-alpha.1`**（通道 `alpha`）

共 **11** 个包：自研 **7** / 第三方 **4**。
逐条的版本、作者、上游仓库、许可与非最新版声明见
[`collection/README.md`](../collection/README.md)；机器可读清单（含逐条 sha256）见
[`collection/manifest.json`](../collection/manifest.json)。

### 关于来源标注

- **作者**按包内 `package.json` 的 `author` 字段填写
- 该字段缺失时，**依据包内 `README.md` 声明的上游核实**
- 核实不到就写「**未注明**」，**不留空、不猜测**

**第三方插件的版权归各自原作者所有。** 本仓库仅做离线打包与索引，不修改其许可声明。
如你是某个插件的原作者、希望调整或移除收录方式，请开 Issue 或直接联系，我们会立即处理。

## 四、目录结构与不可变性

```none
collection/
├─ README.md                  # 收录介绍：面向用户的说明
├─ README.en.md               # 英文版
├─ SPEC.md                    # 收录规范：面向贡献者的规范性文档
├─ manifest.json              # 机器可读清单（含 sha256），由脚本生成，禁止手写
├─ collection-notes.json      # 唯一人工维护的文件：版本核实结论与收录理由
└─ snapshots/
   └─ <目录名>/               # 包名去掉 scope，如 @dsh-market/plugin → dsh-market-plugin
      └─ <插件版本>/          # ★ 插件版本，不是 dsh 版本（与 plugins/ 的约定相反）
         └─ <包名>-<版本>.tgz
```

> **注意这一层是插件版本**，与 `plugins/<目录名>/<dsh 版本>/` 的含义**相反**。
> `plugins/` 答的是「该装哪一套」，`collection/` 答的是「当时收录的是哪一版」。
> 详见 [`collection/SPEC.md`](../collection/SPEC.md) §2.1。

快照是**不可变**的：已收录的目录**一律不得修改、覆盖或删除**。
上游发新版时**新增**一个版本目录，旧目录原样保留。

> 快照被改动就意味着 sha256 失效，而 sha256 正是「装回来的还是当初那一份」的
> 唯一保证。改快照等于把这条保证作废。

**唯一例外**：引导插件 `dsh-plugins-market` 的 tarball 就是本仓库的构建产物，
每次构建都会重新生成，因此它的快照是「**随构建同步刷新**」而不是永久冻结 ——
规则见 [`collection/SPEC.md`](../collection/SPEC.md) §2.4。

## 五、完整性校验

每个快照都有 `sha256`，记录在 [`manifest.json`](../collection/manifest.json) 里。
它保证「装回来的和当初验证过的是同一个字节」。

```bash
# 重新生成清单并逐个核对 sha256
node scripts/build-collection.mjs

# 只校验不写盘（CI 用）
node scripts/build-collection.mjs --check
```

校验失败会明确报出哪一项不一致（与 `compatibility.json` 不符 / 快照文件缺失 / sha256 不匹配）。

## 六、怎么安装这些快照

**不需要手动用这里的 tarball。** 在 GUI 里打开左侧「插件市场」→「已验证」页签，
点「安装」即可 —— 市场读的就是这份收录目录，并在装前跑兼容性闸门。

安装流程见[首页「30 秒开始」](../README.md#一30-秒开始)与
[`README-安装说明.md`](../README-安装说明.md)。

---

## 七、怎么新增收录

1. 读 **[`collection/SPEC.md`](../collection/SPEC.md)** —— 收录规则是**强制**的
2. 落实真实来源（版本 / 作者 / 上游仓库 / 许可，四项齐全）
3. 在隔离环境里真机验证一次
4. 按规范登记，并跑 `node scripts/build-collection.mjs`

入库的完整动作见 [`CONTRIBUTING.md` 第 3.5 步](../CONTRIBUTING.md#第-35-步登记收录快照-强制)。
**没把握就先进 Issue 问 —— 不要猜版本号，也不要猜作者。**
