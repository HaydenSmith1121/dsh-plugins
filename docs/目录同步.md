# 目录同步（每日采集）

**[← 回到首页](../README.md)**

> 本页说明 `catalog/` 是怎么来的：采集什么、从哪几路合并、版本号怎么定、
> 什么时候推进时间戳、花多少 GitHub 配额，以及**本地怎么跑一遍**。
>
> 一句话：`catalog/plugins/<slug>.json` 与 `catalog/index.json` **全部由
> [`scripts/sync-catalog.mjs`](../scripts/sync-catalog.mjs) 生成**，它是仓库里
> 唯一会写 `catalog/` 的东西。手写的会被下一轮覆盖，且 CI 的 `--check` 会直接报不一致。

---

<a name="what"></a>

## 一、它产出什么、为什么必须每天跑

| 产出 | 内容 |
|---|---|
| `catalog/plugins/<slug>.json` | 一个插件一份配置：版本号 / `versionSource` / 收藏量 / 仓库地址 / 许可 / **安装方法** / 信任层级 / 审核证据 |
| `catalog/index.json` | 由上面**派生**的紧凑索引（列表页只读它）+ `counts` |

目录是本仓库的**运行时数据**：市场面板显示的版本号、能不能升级、按什么方式安装，
全部来自这些文件。它们过期的表现很隐蔽 —— 界面照常工作，只是「明明上游发了 0.5.0，
这里还写着 0.4.2」，而用户没有任何办法看出来。所以刷新必须是**自动、定时**的：

```none
.github/workflows/sync-catalog.yml
  on: schedule: cron '0 18 * * *'        # 每天 18:00 UTC = 次日 02:00（北京时间）
      workflow_dispatch: 手动触发，可传 only / limit 两个输入
  permissions: contents: write            # 用工作流自带的 GITHUB_TOKEN 读公开仓库、提交结果
  concurrency: sync-catalog（不取消进行中的那一次）
  timeout-minutes: 90
  Node 22.19 → node scripts/sync-catalog.mjs → node scripts/sync-catalog.mjs --check
             → node plugins-src/dsh-plugins-market/build.mjs    # ★ 重打市场包
             → git status --porcelain -- catalog plugins：有变化才 commit && push
             → commit message：chore(catalog): 定期刷新插件目录（共 N 条）
```

**为什么同步目录还要重打市场包**：市场包内嵌一份**离线兜底目录**（`tier=verified` 那几条，
没网时靠它列插件），它是 `catalog/` 的派生**物**。派生**物**必须和它的输入由同一次自动化
一起提交，否则 main 上会短暂存在「目录是新的、包里的兜底是旧的」——
而 `verify.yml` 那条「用当前源码构建出来的字节必须等于已提交的字节」会在下一次
**别人**的 push 时把这个错位报出来（定时任务用的是 `GITHUB_TOKEN`，它的 push 不触发工作流，
所以错位会一直攒着，最后红在别人头上）。

**为什么这不会变成「每天重打一次包」**：兜底目录是目录的**稳定投影**，不是副本 ——
进包之前会把 `versionCheckedAt` / `stars` / `source.lastSyncedAt` / 索引的 `generatedAt`
这类**登记性**字段一律清空（清空而非删除，字段形状与仓库里那份保持一致）。
留下的只有「这是哪个包、什么版本、从哪儿下、校验和是多少」。
所以目录的日常刷洗不会动到包，只有版本号 / 安装方式这类**实质内容**变了才会产生新字节。

**为什么不会产生「每天一次空提交」**：只有当**内容真的变了**时才推进时间戳（见第五节），
没有实质变化时生成的文件逐字节相同，`git status` 自然是干净的，那个 `if` 就不会提交。

<a name="sources"></a>

## 二、四路合并：数据从哪来

| 路 | 来源 | 进入目录后的层级 | 说明 |
|---|---|---|---|
| ① | `catalog/overrides/reviewed.json` | `reviewed` | 人工审核过的第三方插件，**带审核证据**（审核人 / 日期 / 环境 / 结论） |
| ② | 集合仓库的 `manifest.json` | `verified` | 由插件集合仓库托管 tarball、按 dsh 版本实测过的那批（安装方法固定 `tarball`，带 `url` + `sha256`） |
| ②′ | `catalog/overrides/self.json` | `verified` | 市场插件**自己**那一行。它是唯一由本仓库托管产物的插件，不在集合仓库的清单里 |
| ③ | 公开索引 `plugins.json` | `community` | 社区插件的默认层级 |
| ④ | 已有的 `catalog/plugins/*.json` | 不变 | **上一轮的结果**：人工审核结论、首次发现时间、集合层的安装信息靠它传承 |

**合并规则**（`rank` 比较，层级从高到低 `verified` → `reviewed` → `community`）：

- 同一插件（按 `slug` 归并）**保留层级最高的那一条** —— 优先级由 `tier` 决定，与「第几路」无关：
  同一插件既进了集合清单（`verified`）又被人审核（`reviewed`）时，保留 `verified` 那条，
  因为层级更高的是「我们实测过的那份字节」这个说法
- 层级相同时**先写入者胜**（写入顺序：公开索引 → 集合清单 → self → reviewed；
  实际只有 `community` 之间可能出现同层冲突，而它只有一个来源）
- 因此「既是人工审核过、又出现在公开索引里」的插件保留带 `review` 证据的那条，
  而不是被索引里的裸记录冲掉
- 派生索引 `catalog/index.json` 会**再去重一次**，键是「包名优先、其次 id」
  （与市场面板运行时的 `mergeEntries` 同一口径），免得「索引里看到的」与「打开后看到的」不是同一个

**上一轮的传承**（第 ④ 路）具体传什么：

| 传什么 | 条件 |
|---|---|
| `source.firstSeenAt` / `lastSyncedAt`、`versionCheckedAt`、`metricsCheckedAt` | 总是 |
| `review`（人工审核结论） | 本轮来源没给，且这一条不是 `community` 层 |
| `install`（集合层的 url / sha256 等） | 这一条是 `verified` 层，且本轮没拿到 url |
| `install.spec` | 这一轮安装方法仍是 `npm` 但没带规格，而上一轮是 `npm` |

> **读文件时以文件名为准**，不是以文件内部的 `slug` 字段为准 —— 否则文件被改名后会出现
> 「读的是 A 文件、写回 B 文件」这种静默复制。

### 集合清单从哪读

按顺序尝试，取到就用：

1. 本地目录：`$DSH_PLUGIN_COLLECTION`，或本仓库的**同级目录** `../dsh-plugin-collection/manifest.json`
2. 联网：`https://raw.githubusercontent.com/HaydenSmith1121/dsh-plugin-collection/main/manifest.json`
   （结果缓存到 `.cache/collection-manifest.json`）
3. 离线：直接用上面那份缓存
4. 都没有：**明确记一句「本轮不含自研插件」**继续跑，而不是静默丢掉这一层

公开索引同理：抓不到就用 `.cache/public-index.json`（原始索引约 22 MB，缓存时只留采集需要的
字段）。`.cache/` 不进版本库。

<a name="version"></a>

## 三、版本号与收藏量怎么定

### 3.1 版本解析顺序

```
npm registry  →  GitHub release  →  GitHub tag  →  默认分支的 package.json  →  null
```

| 命中 | 写进配置的 `versionSource` | 细节 |
|---|---|---|
| npm | `npm` | 查 `https://registry.npmjs.org/<name>/latest`（只要几十字节，不拉整包文档） |
| GitHub release | `github-release` | `latestRelease.tagName` 去前缀后取版本号（`v1.2.3` / `dsh-x-v1.2.3` / `release-1.2.3` → `1.2.3`），同时把 `latestRelease` 事实写进去 |
| GitHub tag | `github-tag` | 同上，但没有 release 记录 |
| 默认分支 `package.json` | `package.json` | 仓库里声明的版本 |
| 都没有 | `none` | `version: null` —— **如实留空，不发明** |

> **绝不因为「这一次没查到」就把已知的值抹掉。** 见下面 3.3 —— 这条与「上游把 release 删了」
> 是两件事：**确定的没有**（404）才写 `none`；**这次没查成**（超时 / 限流 / 5xx）
> 要沿用上一轮的结论。两者混为一谈的代价实测过：一次 CI 运行改写了 1004 个文件。

### 3.3 「没查成」与「查不到」必须分开（2026-09 实测踩过）

`resolveNpmLatest()` 返回三种结果，不是笼统的 null：

| status | 含义 | 调用方怎么做 |
|---|---|---|
| `ok` | 查到了 | 用它（前提是同源校验通过） |
| `not-found` | **确定**这个包不在 npm 上（HTTP 404） | 按顺序回退到 GitHub |
| `error` | 这次没查成（超时 / 429 / 5xx，已退避重试 3 次） | 上一轮有值就**保留**，不回退 |

为什么必须分开：GitHub Actions 的 runner 是**数据中心 IP**，npm registry 对它限流明显。
并发 8 路时 npm 命中率掉到 **17%**（本地同一条命令是 65%），于是那 83% 全部「回退到
GitHub」，把上一轮从 npm 拿到的版本号换成了 release/tag 的号 —— 一次运行 1004 个文件变更，
而**上游什么都没变**。第二天限流缓解又换回去，版本号在界面上会真的来回跳。

配套的两条：

- **npm 并发 8 → 4**：数据中心 IP 上并发越高，命中率反而越低。
- **GitHub 那一轮同一条规矩**：这一批没拿到该仓库的数据时（可能是仓库没了，也可能是
  整批失败 / 预算用完），只要上一轮有值就保留，不抹成 `null` —— null 在界面上是
  「版本未知」，比一个稍微旧一点的版本号糟得多。代价是「仓库真被删了」会延后一轮才发现，
  而那种情况下上游索引通常也一起没了（记录会被移除）。

采集结束时会打印一行 `本轮没查成、沿用上一轮结果的：N`。这个数字突然变大，
基本就是本机/CI 到 npm 或 GitHub 的线路出了问题，而不是上游有什么变化。

### 3.2 npm 的**同源校验**（这条最容易被忽略，代价也最大）

公共索引里的 `name` 与真实 npm 包名**没有任何保证关系**。实测 `dsh-plugins-market` 在 npm 上
确实存在（版本 `0.1.0`），但那是**另一个人的、完全无关的包**。拿它当版本号写进目录，
用户看到的就是一个漂亮且彻底错误的数字。

所以 npm 这一路有两个前提，缺一不可：

1. **只有配置文件里本来就是干净的 npm 规格时才去查 npm**（也就是上游 README 自己写的是
   `dsh plugin add <包名>`）。拿仓库名去 npm「碰运气」是错的，而且很贵
2. **npm 上那个包声明的 `repository` 必须指向同一个仓库**：两边都取出 `owner/repo`
   （先归一化 `git+` / `ssh://git@github.com/` / `git@github.com:` / `.git` 后缀）再小写比较，
   不一致就**不采信**，改走 GitHub

### 3.3 收藏量

- 走 GitHub 的一路：`stars` / `forks` / `pushedAt` **以 GitHub 为准**（比上游索引新），
  索引里的值只作为兜底；顺带在字段为空时补 `license` / `homepage` / 仓库里真实的包名
- 走 npm 的一路：包文档里没有 star 数，这些字段留给索引里的值
- **集合层（`source.kind === "collection"`）不查 GitHub**：它们的 `repo` 指向集合仓库本身，
  查出来会让 6 个插件显示同一个 star 数 —— 那是个假事实

`install.method` 为 `npm` 的条目走 npm（实测约 2000 条，**8 路并发**，串行要十分钟）；
其余走 GitHub。

<a name="budget"></a>

## 四、GitHub 数据怎么取、花多少配额

GitHub 的配额是 **5000 点/小时**，逐个仓库打 REST 必然撞墙（7487 个仓库光 releases 就要
7487 次请求）。所以全部走**批量 GraphQL**：

- 一次查询里用别名把 **50 个仓库**（`DEFAULT_BATCH`）并排问，每个仓库一次拿全：
  star / fork / pushedAt / homepage / license / latestRelease / 最新 tag / 默认分支的 `package.json`
  —— 「一个仓库一次往返」变成「一个批次一次往返」
- 计费按响应里的 `rateLimit.cost` 实际累加；**拿不到 cost 时按 1 点/仓库保守估算**
  （免得配额被打爆才发现）
- 一轮全量**最多约 150 批**（7487 ÷ 50；带干净 npm 规格的那批走 npm，不占 GitHub 配额）；
  工作流里的实测结论是 7000+ 个仓库「只花掉一百多点点数」，远在 5000/小时 之内
- `--github-budget`（默认 **4500**）是提前刹车：到点就停，剩余仓库留到下一轮，并明确打印
  「已达本次配额上限」
- 拿不到 token 时**不猜**：GitHub 侧的版本号与 star 数留空，并打印一句提示

用的 token 按顺序取环境变量：`GITHUB_TOKEN` → `GH_TOKEN` → `DSH_CATALOG_GITHUB_TOKEN`。
GitHub Actions 里用工作流自带的 `secrets.GITHUB_TOKEN`，读公开仓库足够。

> 部分失败是**正常**的（仓库改名 / 删除 / 转私有）：GraphQL 的 `errors` 只记下来，
> 对应的别名节点为 `null`，不会整批丢掉。

<a name="timestamps"></a>

## 五、时间戳策略：内容没变就不动

每天一次定时任务，如果无脑刷新 `lastSyncedAt`，7000 个文件会天天全部显示为「已修改」，
真正的变更就被噪音淹没。规则：

| 字段 | 什么时候推进 |
|---|---|
| `versionCheckedAt` | `version` 或 `versionSource` **真的变了** |
| `metricsCheckedAt` | `stars` / `forks` / `pushedAt` **真的变了** |
| `source.lastSyncedAt` | 记录内容**真的变了**（比较时会忽略上面三个时间戳与 `lastSyncedAt` 本身） |
| `source.firstSeenAt` | 只在**第一次**发现这个插件时写 |
| `index.json` 的 `generatedAt` | **上游公开索引**的生成时间（不是本仓库的运行时刻），写 `null` 也可比 |

内容一致时，采集器直接把**上一轮的对象整体沿用**，保证写出去的文件逐字节相同 ——
所以 `git` 上不会出现「只有时间戳变了」的假变更，`--check` 也能做**逐字节**比较。

**条目消失时怎么办**：

| 情况 | 处理 |
|---|---|
| `tier=community` 且 `source.kind=public-index` | 直接删除（可再生） |
| 其它（带人工结论、或来自集合层 / 覆盖层） | **一律保留** —— 上游改名或索引抖动不该抹掉人工结论 |

<a name="local-run"></a>

## 六、本地怎么跑

```bash
# ① 完整采集 + 写盘（联网；GitHub 侧建议带 token，否则版本与 star 会留空）
node scripts/sync-catalog.mjs

# ② 只读校验：只读磁盘，不联网、不写盘（CI 用）
node scripts/sync-catalog.mjs --check

# ③ 不联网，把磁盘上已有的配置归一化并重建 index.json（会写 index.json，但不删任何文件）
node scripts/sync-catalog.mjs --offline

# ④ 只刷新一个插件（调试用；参数可以是 slug 或原始 id）
node scripts/sync-catalog.mjs --only nagi-ovo__dsh-ads
node scripts/sync-catalog.mjs --only Nagi-ovo/dsh-ads

# ⑤ 只解析前 N 个（**试跑**，见下面的警告）
node scripts/sync-catalog.mjs --limit 20
```

| 参数 | 作用 |
|---|---|
| `--check` | **只读**：不联网、不写盘。逐条检查 ① 每个 `catalog/plugins/*.json` 能否**原样往返**（归一化再序列化必须与磁盘字节完全相同）② `index.json` 是否恰好是这些文件的派生结果（比较时忽略 `generatedAt`）③ 文件数与索引条数是否相等。有问题退出码 1 |
| `--offline` | 不联网，把磁盘上已有的配置归一化后落盘，并重建 `index.json`。**不删文件、不新增条目** —— 它不等于「刷新目录」 |
| `--only <slug\|id>` | 只处理这一个插件（其余条目沿用上一轮已解析的版本号，不会被抹空） |
| `--limit N` | 只解析前 N 个 |
| `--allow-partial-write` | 允许 `--limit` 的结果落盘（**默认拒绝**） |
| `--github-budget N` | 本轮 GitHub GraphQL 最多花多少点，默认 4500 |
| `--quiet` | 少打印 |

> **三条路径的能力边界别混**：只有**不带参数**那条会联网、才会新增或删除配置文件。
> `--check` 连写盘的能力都没有（`checkOnDisk()` 里没有任何写操作）；
> `--offline` 会写 `index.json` 但从不删文件。
>
> 这条边界曾经被破坏过一次，代价是 `--check` 删掉了 7482 个配置文件并 exit 0
> （详见 `docs/注意事项.md`）。现在 CI 里有一条断言：跑完 `--check` 之后
> `git diff` 必须为空。

> ⚠️ **`--limit` 默认是试跑，不写盘。** 它只解析前 N 个插件，其余条目沿用上一轮的版本号；
> 真要落盘得显式加 `--allow-partial-write`。要生成完整目录就**去掉** `--limit`。

> ⚠️ **改完人工覆盖层必须重跑一次采集。** 只改 `catalog/overrides/*.json` 而不跑
> `node scripts/sync-catalog.mjs`，`catalog/plugins/*.json` 里的 `tier` 还是旧的，
> 界面上的标签也就还是旧的。

`.github/workflows/verify.yml` 的 `catalog` 任务三件事：跑一遍 `--check`；
断言它**没有改动工作区**（只读性的回归断言）；再数一遍 `catalog/plugins/*.json`
的份数是否等于 `index.json` 的 `counts.total`。

<a name="add-reviewed"></a>

## 七、怎么加一个「已审核」插件

`catalog/overrides/reviewed.json` 是**唯一必须由人写**的插件清单，也是三层里 `reviewed`
的唯一来源。收录一条的**最低要求（缺一不可）**：

1. 在一台真机上，用它**声明适配的那个 dsh 版本**实际装进隔离环境
   （`~/.dsh-dev`，见 [`README-开发环境隔离.md`](../README-开发环境隔离.md)）并启动成功；
2. 记录 dsh / node / pnpm 版本、tarball 或 spec、sha256（能算就算）、以及启动输出里的关键行；
3. 明确它的 peer 约束是否与本仓库基线兼容，结论写进 `peerNote`；
4. 说清楚它有没有副作用（写全局配置、起后台进程、需要联网 / 登录 / API Key）；
5. `review.reviewedAt` / `review.dshVersion` / `review.verdict` 三个字段必须填。

### 步骤

```bash
# ① 先让助手把探测与核对过程跑成一份草稿（不要凭印象手写）
node scripts/market-review.mjs <owner/repo | npm 包名 | 插件 id>
node scripts/market-review.mjs <owner/repo | npm 包名 | 插件 id> --json   # 只要 JSON
node scripts/market-review.mjs <owner/repo | npm 包名 | 插件 id> --write  # 直接追加进 overrides/reviewed.json

# ② 复核结论：把带 ★ 的字段补全，必要时补齐 install/peer 字段
#    （--write 只是追加草稿，它不是「审核通过」的同义词）

# ③ 重新生成目录（必须！）
node scripts/sync-catalog.mjs

# ④ 提交前自检（CI 会跑同一件事）
node scripts/sync-catalog.mjs --check
```

`review.verdict` 的含义：

| 取值 | 含义 |
|---|---|
| `ok` | 实测可用，与本仓库基线兼容 |
| `ok-with-notes` | 实测可用，但有需要注意的地方（写进 `review.notes`） |
| `broken` | 实测不可用 —— **收录它是为了给用户一个明确的「别装」信号** |

> **本层条目走 `github:` / npm 规格，本仓库不重新分发它们的字节**，所以 `sha256` 通常为
> `null`：第三方插件的字节完整性由上游仓库自己保证，这里改记**验证时的 commit**
> （写进 `review.evidence`）。
>
> 收录标准、字段含义与「怎么核实来源」的完整义务见
> [`CONTRIBUTING.md`](../CONTRIBUTING.md#review-flow) 与
> [`docs/插件清单与来源.md`](./插件清单与来源.md#fields)。

## 八、几个容易踩的点

| 现象 | 原因 / 正确做法 |
|---|---|
| `--check` 报「内容不是归一化后的形态」 | 有人手工改过配置文件（字段顺序 / 空值写法 / 缺字段）。跑一次 `node scripts/sync-catalog.mjs --offline` 就能把它归一化回去，别手工对齐 |
| `--check` 报「index.json 与派生结果不一致」 | 改了配置文件却没重建索引。`node scripts/sync-catalog.mjs --offline` |
| `--check` 报条数对不上 | `catalog/plugins/*.json` 的份数与 `index.json` 的 `counts.total` 必须相等（一条配置 = 一条记录）。差得多半是手工删/加了文件 —— 跑一次完整采集 |
| `--check` 跑完 `git status` 有改动 | **不该发生**：`--check` 是只读的（CI 里有断言钉住）。出现了就是回归，别提交，先去 `scripts/sync-catalog.mjs` 看分流 |
| 版本号大片变成 `null` | 跑过 `--limit` / `--only`？未选中的条目会沿用上一轮的值，若上一轮本来就是空的就会是 null。重跑一次完整采集 |
| GitHub 侧全是空 | 没有 token（`GITHUB_TOKEN` / `GH_TOKEN` / `DSH_CATALOG_GITHUB_TOKEN`），或 `--github-budget` 用完了 |
| 集合层的 6 个插件没进目录 | 读到集合仓库失败：确认本地同级目录存在、或设 `DSH_PLUGIN_COLLECTION`、或联网可达 |
| 明明改了 `overrides` 但界面没变 | 忘了重跑采集；或者市场面板的目录有 30 分钟 TTL，点一下「刷新目录」 |
| 每晚都产生一次「只有一个数字变了」的提交 | 有人把 tarball 自己的 sha256 **或字节数**写进了会进包的说明文字 / 记录里 —— 那是死循环（tarball 内容取决于那个数字，那个数字又取决于 tarball）。校验和属于 `.tgz.sha256` 边车文件，`install.bytes` 一律留空 |
| 只是刷了一次目录，市场包却变了 | 兜底目录里混进了**登记性**字段（时间戳 / star 数 / 上游元信息）—— 它们每次采集都会变，但和「离线能装什么」无关。进包前必须清空，见 `build.mjs` 的 `[0]` 一节；两条回归用例钉着这条不变量 |
| CI 报「产物必须已提交」但源码一个字节没改 | 先看 diff 的形态：`Bin N -> M`（**不同长**）多半是真忘了重新构建；`Bin N -> N`（**同长**）则几乎一定不在源码里，而在归档容器/压缩器的平台相关字节上 —— 历史事故是 zlib 把**编译期**确定的 OS 码写进 gzip 头第 9 字节（Windows `0x0a` / Linux `0x03`），现在容器由 `build.mjs` 自己写死（`OS=255`） |
