# dsh-plugins-market

本仓库（[HaydenSmith1121/dsh-plugins](https://github.com/HaydenSmith1121/dsh-plugins)）自带的**可视化插件市场**：
装进 DeepSeek Harness 左侧导航栏，在界面里浏览、检查、一键安装插件。

它和公共市场（`@dsh-market/plugin`，数据源 dsh.market）的**根本差别是安全模型**：
本插件存在的唯一理由是「别把 harness 装坏」，所以每一次安装都先过一道兼容性闸门，
失败自动回滚。可以把它理解成「带刹车的一键安装」。

---

## 〇、这一版的核心：市场与插件是分离的

| | 市场（本仓库） | 插件（[dsh-plugin-collection](https://github.com/HaydenSmith1121/dsh-plugin-collection)） |
|---|---|---|
| 装什么 | **目录**：`catalog/plugins/<slug>.json`（一个插件一个配置文件） | **插件本体**：各插件的 tarball、源码与 `plugins/<id>/plugin.json` |
| 谁维护 | 每日 GitHub Actions 自动刷新 + 人工审核层 | 插件作者 |
| 变更影响 | 某个插件发新版 → 只改**那一个配置文件**，本插件不用换版本号 | 发新版 → 加一个 tarball、更新 `plugin.json`、重跑 `build-manifest.mjs` |

**安装一个插件 = 把那个插件自己的配置文件读下来，再按它写的 `install.method` 去装。**

这不是实现细节，而是这一版唯一重要的产品约定：

- 索引（`catalog/index.json`）只负责让用户**看到**有哪些插件 —— 它是派生的、可重建的；
- 真正动手时一律去读 `catalog/plugins/<slug>.json`。**读不到就不装**，
  而不是拿索引里的字段猜一个安装方法。按索引猜出来的方法会把「装什么」这件事
  从「配置说了算」变成「代码猜的」，而那种错非常安静：装是装上了。

`install.method` 的取值：`tarball`（url + sha256，托管在某个仓库里）、
`npm`、`github`（`github:owner/repo`）、`skills`（上游走 skills 机制，不是 dsh 插件）、
`manual`（没有可靠的一键方式）。

## 一、一份平铺列表，不分级

> ★ **0.5.0 去掉了三个信任层级**（`verified` / `reviewed` / `community`）。
> 那一套回答的是「维护者该不该为这个插件背书」，而用户真正要回答的只有一个问题 ——
> **这个插件我这儿装不装得上**。那个问题由**装前检查**当场判：它看的是真实的
> node / pnpm / dsh 版本、profile 现状、候选包声明了什么，比一个维护者贴的标签准得多，
> 也不会过期。少一层需要维护、需要解释、还会悄悄失效的分类。

所以现在：

- 配置文件里**没有 `tier` 字段**，索引里也没有；`counts` 只有一个 `total`。
- 界面只有一个列表，**没有层级页签、没有层级筛选、卡片上没有层级角标**。
- 顶部那行环境信息（dsh / node / pnpm / 矩阵）也一并去掉了 —— 需要时在「已装」页看。
- 顶部只留一组与**你自己**有关的筛选器：`全部 / 已安装 / 可升级 / 我收藏的`，底部按需分页。

**装前检查仍然在，而且它是唯一决定「能不能装」的东西**：

| 结论 | 含义 | 能不能装 |
|---|---|---|
| 有**不可覆盖的致命项** | 明确装不上（peer 精确 pin 到更高版本、声明的 patch 文件不在包里……） | 不能，按钮点不动 |
| 有**可覆盖的致命项** | 装上去大概率也没用（例如包里没声明 `dsh.bundle`，加载不起来） | 勾一次确认才能强装 —— **这是唯一需要确认的场合** |
| 只有警告 / 全部通过 | 可以装 | 能 |

> **为什么不再要求「装未审核插件先勾确认」**：让用户为**每一个**社区插件点一次
> 「我知道有风险」，换来的不是安全，而是闭眼点确定的习惯；而真正该停下来看的
> （「这个包装上也加载不起来」）反而淹没在同一个对话框里。现在那个确认只对应后者。

> **字节来源仍然如实区分**（装前检查里的 `cand.provenance`）：字节由本仓库托管时，
> 下载的是我们自己的 tarball、`sha256` 逐字节核对、可离线安装；装的是上游产物时
> （npm / GitHub），本仓库不转发它的字节，只能做静态探测。
> 这说的是「我们查得有多细」，不是「这个插件可不可信」—— 它不影响能不能装。

> **为什么不能直接复用上游给的安装命令**：公开索引实测 7487 条里混着
> `curl … | sh`、`pip install`、`brew install`、`npm install -g` 这类根本不是
> dsh 插件安装的命令。所以「提取干净的 npm / GitHub 规格」这件事被前移到了
> **采集阶段**（`scripts/sync-catalog.mjs`），结果写进配置文件的 `install.method` /
> `install.spec`；本插件只执行配置文件，不再现场解析命令。
> 唯一还留在运行时的兜底是：配置文件没给规格、但条目的仓库地址是干净的 GitHub 仓库 ——
> 这时推导 `github:owner/repo`（pnpm 直接解析那个仓库，不会装进来一个同名无关的包）。

> **「收藏量」是 GitHub star 数**，由每日采集任务刷新，写在配置文件的 `stars` 字段里。
> 界面上的「收藏」是本插件的**本地标记**，两者不是一回事（见第四节）。

## 二、装前闸门：到底检查什么

严重度分三档，这是整套设计的核心：

| 级别 | 含义 | 能否继续 |
|---|---|---|
| `fatal` + 不可覆盖 | **已知确定有害** | ❌ 硬拦截，界面上不提供覆盖入口 |
| `fatal` + 可覆盖 | 我们**无法确认**它安全（不是确认它不安全） | 勾选「我已阅读上述风险」后可继续 |
| `warn` | 已知软风险 | 可以继续，但界面必须如实说明 |

### 环境层

| 检查 | 级别 |
|---|---|
| Node 版本低于本仓库验证下限 | fatal（可覆盖） |
| 找不到 dsh 安装目录 | fatal（不可覆盖） |
| dsh 版本不在兼容矩阵里 | fatal（可覆盖） |
| dsh 版本被标记为不支持 | fatal（**不可覆盖**），并给出该升到哪个版本 |
| dsh 版本 == npm `latest` 通道（静默降级陷阱） | warn |
| pnpm 缺失 / 与 dsh 不在同一 Node | fatal |
| pnpm 版本低于验证下限 | warn |

### profile 层

| 检查 | 级别 |
|---|---|
| `file:` 依赖指向的 tarball 已不存在 | fatal（**不可覆盖**）—— 见第八节真实案例 |
| `pnpm-workspace.yaml` 丢了 `packages`/`nodeLinker`/`autoInstallPeers` | fatal（可覆盖，可一键修复） |
| bundles 里有既非依赖也非内置的孤儿项 | warn（可一键修复） |
| 已装版本与声明版本漂移 | warn |
| `allowBuilds` 有未决定的占位符 | warn（安装前自动补好） |

### 候选包层

| 检查 | 级别 |
|---|---|
| 精确 pin 的 `@deepseek-ai/*` **高于**本机版本 | fatal（**不可覆盖**）—— 缺具名导出会让整棵树挂 |
| 精确 pin 的 `@deepseek-ai/*` **低于**本机版本 | warn（向后兼容，实测可用） |
| peer 范围按 npm 语义不匹配 | warn（`autoInstallPeers: false`，peer 不参与安装） |
| 声明了 `dsh.bundle.patch` 但包里没有该文件 | fatal（**不可覆盖**）—— boot 期必然失败 |
| 没有声明 `dsh.bundle.patch` | fatal（可覆盖）—— 装了也永远不会加载 |
| tarball 的 sha256 与目录记录不符 | fatal（**不可覆盖**） |
| `engines.node` 不满足（注意 `^22.19.0 \|\| >=24.0.0` **排除 23.x**） | fatal（可覆盖） |
| 已知共存冲突（`dsh-opencode-go` ↔ `dsh-opencode-go-plus`） | fatal（**不可覆盖**） |
| 带 `preinstall`/`install`/`postinstall` 脚本 | warn（供应链信号） |
| insert 行 id 与现有装配树冲突 | warn |
| 包内疑似凭据文件（`.env` / `.pem` / `.npmrc` …） | warn |
| 字节来自上游（非本仓库托管） | info：说明判定只能做静态探测 |

> peer 的两档判据是**用仓库里两个真实数据点校准**出来的，不是拍脑袋：
> `dsh-opencode-go-plus` 精确 pin 到 **更高**版本 → 真实事故（整棵树挂）；
> `dsh-receipt` 精确 pin 到 **更低**版本 → 实测正常，若按「pin 不等即致命」会把它自己拦掉。

## 三、事务化安装

一次安装就是一次事务：

```
[0]   复核闸门（必须放行）；已经是最新版本时在这里直接短路
[0.5] profile 装前体检：断链的 file: 依赖 / workspace 文件缺失 —— 见第七节
[1]   取安装包：本地仓库优先（离线）；没有就联网下载并校验 sha256
[2]   备份 profile 的 5 个状态文件 → $DSH_HOME/storages/dsh-plugins-market/backups/
[3]   事前补好 allowBuilds（读**当前**文件再合并，绝不重放旧快照）
[4]   升级场景先 remove 旧版本，再 add 新版本（见下面「为什么必须 remove 再 add」）
[5]   跑 dsh plugin add
         ★ 成功判据是 **pnpm 退出码**，不是「node_modules 里有没有文件」
         ★ 撞 ERR_PNPM_IGNORED_BUILDS 时自动补 allowBuilds 并重试一次
[6]   校验三层：依赖层 / 注册表层 / 装配层
[7]   任何一步失败 → 用 [2] 的快照回滚，并重新链接 node_modules
```

**为什么第 6 步的「注册表层」是重点**：pnpm 非 0 退出时 dsh 会直接 return，
**不会**把包追加进 `dsh.profile.bundles` —— 这一步完全静默，表现为
「装上了但 GUI 里没有」。这是本插件存在的直接原因。

安装成功后界面会提示：**新增的 bundle 是在启动时合成的，必须重启 dsh web 才会出现。**

### ★ 安装是一个**可观察、可中止**的后台任务（0.2.0）

早先的形态是：点安装 → 一次 HTTP 请求里同步跑完整个安装 → 请求返回才更新界面。
那条路径有三个致命处，正是「点了安装，长时间装不上，而且只能干等」的全部原因：

| 问题 | 根因 | 现在 |
|---|---|---|
| 页面完全没反应 | 安装用的是 `spawnSync`，**把 Node 的事件循环整个堵死**：安装期间这个进程既不能处理下一个请求，也无法把自己的进度报出去 | 全程 `spawn` + 临时文件重定向输出，事件循环始终可响应 |
| 连中止的请求都进不来 | 同上 —— 处理中止的那条路径也被堵着，没有任何技术手段能中断它 | 安装变成**服务端后台任务**：`install` 立刻返回 `jobId`，进度靠轮询，`installAbort` 用 `AbortSignal` 把中止传到 pnpm 并 `taskkill /T` 杀整棵进程树 |
| 不知道还要等多久 | 界面上只有一句「正在安装…请勿关闭页面」 | 8 个**有名字的阶段** + 已耗时 + **预计剩余区间** + pnpm 实时输出 |

现在界面上能看到的是：

```
● 执行安装（pnpm 解析依赖并解包，通常最慢）        预计还需 40 秒 – 1 分 50 秒
  ▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓░░░░░░░░░░░░░░░░░░
  已用 1 分 12 秒 · 本步已用 48 秒 · 开始于 14:32:07
  ✓ 装前体检  ✓ 取安装包  ✓ 拍快照  ✓ 预置 allowBuilds  ▶ 执行安装  ○ 三层校验  ○ 回滚
  ▸ pnpm 实时输出 (14)
```

三条设计上的取舍：

- **每个阶段有独立硬超时**（装前体检 60s / 取包 180s / 换版 180s / 安装 900s /
  校验 180s / 回滚 300s），另有 15 分钟的总兜底。旧版是「所有步骤一律 900 秒」——
  那是一个不会误杀、但用户要干等 15 分钟才知道失败的值。
- **预计时间是区间，不是精确值**。「预计还需 40 秒 – 90 秒」有用；
  「还需 47 秒」会在 20 秒后变成谎话。区间由阶段典型耗时算出，
  并用本机历史（`$DSH_HOME/storages/dsh-plugins-market/timings.json` 的**中位数**）
  自我修正 —— 中位数而不是平均值，因为安装耗时是长尾分布。
- **长时间没有输出会如实说**。「3 分 20 秒没有新输出 —— 这一步可能卡在网络或依赖解析上。
  可以继续等，也可以中止后改用下面的手动命令。」只提示，不擅自中止。

**可以随时离开安装页**：任务活在服务端，关掉抽屉、刷新浏览器、重新打开页面，
都会自动接回进度（抽屉标题上也有「安装进行中 · 查看进度」的入口）。

> 同一时刻只允许一个写 profile 的任务。两个 pnpm 同时改一个 profile 必然互相破坏，
> 所以第二个安装请求会被明确拒绝（也会被排队），而不是安静地并跑。

### ★ 中止安装

「中止安装」按钮**永远可见**（排队中也能按），点了要**再点一次确认** ——
这一步会杀掉正在跑的 pnpm 并回滚 profile，误触的代价是「装到一半被自己打断」。

发出中止后：先结束 pnpm 进程（连同它的子进程），再用安装前的快照把 profile 还原，
然后如实说明「已中止，profile 已回到安装前的状态」。
**「中止」不会显示成「失败」** —— 那是用户要的结果，不是故障。

### ★ 手动安装：永远是备选项，不是失败后的安慰

不管成功、失败、超时还是被中止，安装抽屉底部都有一份**拿到就能执行**的方案：

```
手动安装（同样的效果，你自己敲命令）
  安装包   D:/repo/plugins/dsh-memory/0.1.6-alpha.1/dsh-memory-0.1.0.tgz
  来源     仓库里的快照 tarball（离线可用）
  sha256   e773678ab7b68139…
  profile  web

  1) 确认安装包在本地（无需下载）        [Test-Path …]        [复制]
  2) 校验 sha256                        [(Get-FileHash …)]   [复制]
  3) 安装                               [dsh plugin --profile web add …]   [复制]
  4) 确认装上了（三层校验）              [3 条命令]           [复制]
  5) 重启 dsh web                       [dsh web]            [复制]
  ▸ 出问题时怎么办（3 条）
```

- 命令按 **PowerShell / bash** 分组，可切换，不会两种语法混着给。
- 每条命令**单独一个复制按钮**（用户真正会做的是「就敲这一条」），
  外加「复制整份方案（纯文本）」与「另存为 .txt / .ps1 / .sh」。
- 每条都配一句「这一步在干什么、失败了说明什么」，以及三条兜底：
  撞 `ERR_PNPM_IGNORED_BUILDS` 怎么办、profile 里有断链依赖怎么办、怎么回到安装前。
- 方案在**装前检查里就给**（不必等失败），因为「如果它卡住我该怎么办」
  这个问题不该等到卡住之后才有答案。

本仓库为目录里**字节由自己托管**的那几条都准备了 tarball（由插件集合仓库
`dsh-plugin-collection` 提供，配置文件里带 `url` 与 `sha256`），
所以「手动装」不是一句空话 —— 拿到的是一个确定存在的文件与一个确定的校验和。
第三方插件则按配置文件里的 `github:` / npm 规格给出等价的手动命令。

### ★ 为什么升级必须先 remove 再 add

profile 里那条依赖指向的是**旧版本的 tarball 路径**：

```jsonc
"dsh-opencode-go-plus": "file:.../dsh-opencode-go-plus-0.2.1.tgz"   // 装的 0.2.1，仓库里已有 0.3.0
```

只做 `add` 的话，pnpm 会认为这个依赖已经满足、`dependencies` 那条规格**原封不动** ——
用户点了「更新到 0.3.0」，**实际装的还是 0.2.1，而且界面显示成功**。
这是最难查的一类「假成功」，所以升级路径固定为 `remove` → `add`。

> 实测记录：隔离环境里 dsh-opencode-go-plus 0.2.1 → 0.3.0 走完整流程通过，
> 事后 `dependencies` 里那条 `file:` 规格确实指向了 0.3.0 的 tarball。
> 步骤日志里会明确打出「移除旧版本（原规格 …）」这一步。

## 四、界面

左侧导航栏「插件市场」图标 → 中央面板。3 个页签：

| 页签 | 内容 |
|---|---|
| 插件市场 | 搜索（服务端检索）、筛选、分页列表、插件卡片。可升级时会显示 `↑N` |
| 已装 | 每个插件的挂载状态与**可升级标记**：已挂载 / **装了但没挂载**（红色，ERR_PNPM_IGNORED_BUILDS 残局）/ 版本漂移；可单独更新、校验、卸载。profile 体检（三层校验、真实启动校验、快照回滚、修复 profile）也在这里 |
| 日志 | 每次检查/安装/回滚/收藏的结构化记录 |

> 0.3.0 起去掉了独立的「体检」页签，能力没有丢：三层校验与真实启动校验在
> **每次安装后自动跑**，手工入口搬到了「已装」页。这符合本插件的取向 ——
> 体检不该是一件要用户记得去做的事。

点「装前检查」「安装」或「更新到 x.y.z」会打开**检查抽屉**：按严重度分组列出每一项、
给出可读原因与建议动作，并显示**将要执行的确切安装规格**。
被判定为硬拦截时，「开始安装」按钮直接禁用。

点下安装之后，这个抽屉会变成**进度抽屉**：当前阶段、已耗时、预计剩余区间、
进度条、阶段清单、pnpm 实时输出、「中止安装」按钮，以及始终在底部的手动安装方案
（细节见第三节）。**关掉抽屉不会中止任务** —— 抽屉标题上会留一个
「安装进行中 · 查看进度」的入口。

profile 层面有问题时（最常见的是断链的 `file:` 依赖），面板顶部会有一条
**不折叠的黄色横幅**：说明它是谁、为什么会拖慢所有安装，并给一个可点的
「移除断链依赖」修复（会先备份 profile，失败自动回滚）以及等价的手动命令。

### 安装按钮的三种形态

服务端把「仓库里现在是什么版本」与「node_modules 里真实装的版本」比一遍，
每个插件都会带上一个 `installState`。界面**只做展示**，不在浏览器里比版本号 ——
semver 的预发布规则一错，「已是最新」就会说反，而这种错在界面上完全看不出来。

| 状态 | 按钮 | 说明 |
|---|---|---|
| `not-installed` | 蓝色「安装」 | 可以装 |
| `current` | **灰色「已安装」，禁用** | 已经是最新，没有可做的事 |
| `upgradable` | 蓝色「更新到 x.y.z」 | 仓库里有更新的版本 |
| `older` | 「重新安装」 | 装的比目录里还新（降级场景，交给用户决定） |
| `unknown` | 「重新安装」 | 版本无法比较 —— **不置灰** |

两条判据值得记下来：

- **已是最新时，闸门也直接短路**，不只是把按钮画灰。否则用户还能点开「装前检查」、
  勾风险确认、然后装出一个一模一样的版本 —— 那是纯粹的误导。
  这条在服务端和客户端各拦一次（`install` 会返回 `refused: true` 且 `steps` 为空，
  一个文件都不会动）。
- **无法判定时绝不置灰**。公共索引条目（`github:` / npm 规格）永远拿不到
  「仓库里现在是哪个版本」，这时一律 `unknown`，既不显示「更新」也不禁用按钮。
  宁可少一个提示，也不能把「算不出来」说成「已是最新」。

### 收藏

> ★ **0.5.0 删掉了点赞。** 它和收藏在数据形状上一模一样，区别只是「一个数字大一点好看」
> —— 而这个数字**只统计你自己点过的**（本插件没有后端，没有别人的赞可看）。
> 一个只有自己看得见、含义又与收藏重复的按钮，纯粹是界面噪音。收藏留着：它有实际用处
> （「我收藏的」筛选，找得回装过 / 想装的插件）。

收藏是**纯本地标记**，落在 `$DSH_HOME/storages/dsh-plugins-market/user-data.json`：

```json
{ "schemaVersion": 1, "updatedAt": "…", "items": { "dsh-memory": { "favorited": true } } }
```

- 不上传、不做排行榜 —— 本插件没有后端，**假装有全局热度是骗人**，
  所以界面上如实写成「（记在本机）」
- 取消收藏后整条记录会被删掉，文件不会随着浏览历史无限膨胀
- 文件损坏时降级成空，但**绝不覆盖**它 —— 里面是用户自己点出来的东西，
  宁可丢一次显示，也不能丢数据
- **老数据里的 `liked` 不再读，也不主动删**：升级前落盘过的条目原样留在文件里，
  只是不再展示、也不再统计。主动删用户数据比留一个没用的键更糟

顶部筛选器可以直接筛出「我收藏的」（以及「已安装 / 可升级」）。

## 五、性能

目录现在的形态变了，性能问题也跟着变了 —— **不再需要拉一份 22 MB 的索引**。

| | 旧（≤0.3.0） | 现在（0.4.0） |
|---|---|---|
| 列表数据源 | 公共索引 `plugins.json`，未压缩约 22 MB、gzip 后 4.8 MB | 本仓库的 `catalog/index.json`，仓库里是静态文件，带 ETag |
| 首次/刷新 | 全量下载，实测 28 秒 – 2 分钟（取决于线路） | 目录没变时服务端答 **304**，传输量为零 |
| 缓存 | 6 小时 TTL 的瘦身副本 | 30 分钟 TTL；命中缓存直接返回，不联网 |
| 单条详情/安装 | 索引里的字段 | 按需拉 `catalog/plugins/<slug>.json`，落盘缓存 |

- 三层目录**并发**拉取这件事不再需要 —— 目录只有一个来源。
- 检索与分页仍然全部在**服务端**完成（7000+ 条），浏览器只收当前页。
- 刷新之后界面会**如实报出目录来源**（远程最新 / 目录未变 304 / 本地缓存 /
  离线包内快照）。来源是缓存或包内时必须显式说出来 ——
  那意味着显示的版本号可能不是最新的，这是用户唯一能判断的依据。

## 六、零运行时依赖

服务器半**只用 Node 内置模块**，客户端半**只用 `react`**（shell 的基线模块表里就有）。

这不是洁癖：每多一个依赖就多一分 pnpm 解析失败 / `ERR_PNPM_IGNORED_BUILDS` /
离线不可用的风险，而本插件存在的意义正是「别把 harness 装坏」。
所以 semver 判定、tar 只读访问、YAML 局部合并都是自己实现并有单测覆盖的。

同理，客户端半**不打包、不转译**（源码就是可运行的经典脚本），
少一层构建就少一类「产物与源码不一致」的故障。

**包内只放一份很小的离线兜底目录**（`install.method=tarball` 的那几条 + 本插件自己）。
完整目录（7000+ 条）**不进包** —— 打进包意味着每次目录变化都要重打市场包并换版本号，
而那正是这一版要拆掉的东西。没网时市场至少还能把这几条列出来并装上。

**已知限制**（界面上会讲清楚）：

- 客户端半的错误在 CLI 侧查不出来 —— 例如注册 id 写错会导致浏览器白屏而服务端一切正常。
  本仓库为此有两个 headless 测试把 bundle 真跑一遍：
  `test/client-bundle.test.mjs`（注册形状）与 `test/panel-render.test.mjs`
  （把 Panel 渲染成元素树，逐条断言按钮的禁用态与文案）。
  后者抓到过一个真实问题：`Btn` 里 variant → class 的映射写成了 if/else 链，
  新增 `"update"` 时既不匹配也不报错，按钮照样渲染、能点、文案也对，
  只是**完全没有样式**。这种静默降级界面上极难发现，所以现在改成表驱动，
  并有一条「每个用到的 variant 都必须真的有样式类」的回归测试。
- `bootVerify` 会在同一个 profile 上再起一个 dsh 进程（用 `--port 0` 避开端口冲突），
  因此默认**不**自动执行，需要用户显式点击。

## 七、开发

```bash
node build.mjs             # 生成包内兜底目录 + 组装产物到 .build/package + 打包 tarball
node build.mjs --check     # 只校验产物是否与源码一致（CI / 提交前）
node test/run.mjs          # 跑全部测试
node test/smoke-server.mjs # 服务器半冒烟自检（import / ETA / 排队 / 中止 / 体检）
node test/iso-api.mjs <token>        # 打隔离环境 3090 的端到端验收
node test/iso-diag.mjs               # 服务器半逐步计时（定位「哪一步慢」）
node test/prod-untouched.mjs         # 只读确认生产 3080 没被动过
```

> `build.mjs` 现在生成的是**包内离线兜底目录**（`catalog/index.json` 只含
> 字节由本仓库托管的条目 + 每条对应的 `catalog/plugins/<slug>.json`），
> 不再是「完整目录」。完整目录由仓库根的 `scripts/sync-catalog.mjs` 生成，
> 不进包 —— 理由见第六节。

测试分组（`test/run.mjs`）：

| 文件 | 覆盖 |
|---|---|
| `semver.test.mjs` | 版本比较（闸门判定的地基，含预发布规则） |
| `util.test.mjs` | tar 只读访问 / YAML 局部合并 |
| `gate.test.mjs` | ★ 核心安全属性：致命硬拦截 / 可覆盖，以及「不再因为来自公共索引而要求确认」 |
| `state.test.mjs` | ★ 已装状态判定（决定「安装」是否置灰）+ 收藏 + 平铺列表与筛选 |
| `catalog-refresh.test.mjs` | ★ 单条配置文件是安装的唯一依据 + 远程优先 + 304 + 三级回退 |
| `client-bundle.test.mjs` | 客户端注册形状（CLI 侧查不出来的那类错误） |
| `panel-render.test.mjs` | ★ 面板真渲染一遍：按钮禁用态、文案、筛选器、**层级角标确实没了** |
| `install-flow.test.mjs` | ★ 安装交互走一遍：进度 / 预计时间 / 中止 / 手动命令 / 体检横幅 |
| `layout.test.mjs` | 打包布局下的包内资源解析 + 仓库根探测 |

**产物只落在 `.build/package/`**，源码树保持干净（构建不该改动它自己的输入）。

测试跑在**隔离环境**（`DSH_HOME=~/.dsh-dev`，端口 3090）上，不会碰生产 profile（3080）。
`DPM_TEST_HOME` 可以把它指到别处（本机受限环境下就指向了工作区内的一个副本）。

### 改了源码之后必须做的两件事

```bash
node plugins-src/dsh-plugins-market/build.mjs   # 重打 tarball（版本号也要 bump！）
node scripts/sync-catalog.mjs                   # 刷新 catalog/plugins/dsh-plugins-market.json
```

两条都不能省：

- **不重打 tarball** → `plugins/dsh-plugins-market/<dsh版本>/` 下还是旧产物，
  CI 的 `verify.yml` 会用 `git diff` 把你拦下来。
- **不给市场换版本号** → `file:` 指向同一个 tarball 路径时 pnpm 会跳过解包，
  已经装过的人永远收不到新版本。
- **不重跑 sync-catalog** → `catalog/plugins/dsh-plugins-market.json` 里还是旧版本号，
  市场和目录对不上（`--check` 会红，`build.mjs` 的自注册校验也会直接报错）。

往隔离环境装本插件：

```bash
node ../../scripts/dev-env.mjs install ../../plugins/dsh-plugins-market/<dsh版本>/dsh-plugins-market-<版本>.tgz
```

> ⚠️ **改完代码重新打包后，必须 `remove` 再 `add`**。
> `file:` 指向同一个 tarball 路径时，pnpm 会认为 lockfile 是新的、
> **跳过解包**（`Lockfile is up to date, resolution step is skipped`），
> 即使加 `--force` 也只重新链接、不重新解包 —— 你会一直在跑旧代码。

### 实现 0.2.0 时踩到的两个坑（都写进注释了，值得记一笔）

1. **`resolve(proc)` 里的 proc 自己是 thenable** → Promise 规范会去「解开」它，
   也就是调用它自己的 `.then()`，而那个 `.then()` 等的又是同一个 promise：
   **自己等自己，永远不落定**。症状极具迷惑性：子进程明明跑完、输出也拿到了，
   `await` 却永不返回。修法是对外只暴露一个**不带 then** 的纯结果对象。
2. **子进程输出不能走 pipe**。直觉上该用 `stdio: ['ignore','pipe','pipe']`，
   但在受限环境（文件沙箱 / 受限令牌 / 部分 CI 容器）里，子进程的 pipe 需要
   命名管道权限，拿不到就 `spawn EPERM`；更糟的是父进程**只看到子进程挂着不动**
   （close 事件永远不来）—— 表现正好就是「点了安装，一直没反应」。
   现在一律重定向到临时文件，顺带实现了「边跑边读」的实时输出。

## 八、真实案例

本插件的第一批测试就跑出了两个仓库里真实存在的问题：

1. **两个 profile 各有一条指向已删除 tarball 的 `file:` 依赖**
   （生产指向 `dsh-session-cleanup-0.1.1.tgz`，隔离环境指向 `0.1.0.tgz`，仓库里只有 `0.1.2`）。
   只要引用还在，之后**任何** `pnpm install` / `dsh plugin` 操作都会失败或反复重试 ——
   包括「装一个别的插件」。闸门把它作为**不可覆盖的致命项**拦下来；
   0.2.0 起在**装前体检**里提前挡（见第三节的 `[0.5]`），
   界面上还多了一个「移除断链依赖」的一键修复（先备份，失败回滚）。
2. **公共索引里 star 最高的条目并不是 dsh 插件**。
   `ruvnet/ruflo`（7.2 万 star）的 `package.json` 没有声明 `dsh.bundle.patch`，
   装进去只会躺在 `node_modules` 里、永远不会被加载。远程静态探测拦住了它。
3. **0.2.0 的动机就是一次真实体验**：点安装之后长时间没有结果，
   页面只能干等，既没有预计时间也没有出口。查下来是两个叠加的原因 ——
   `spawnSync` 把事件循环堵死（技术上进不来中止请求），
   以及 profile 里断链的 `file:` 依赖让 pnpm 每次都去解析一棵注定失败的依赖树。
   两者现在分别由「服务端后台任务」与「装前体检 + 一键修复」解决。
4. **0.4.0 的动机是「一个插件发版，市场必须跟着发版」**。旧模型下「已验证」层的目录
   是在市场构建时打进包里的，于是任何插件发新版都得重打市场包、并且**给市场换版本号**
   （`file:` 指向同一路径而内容变了时 pnpm 会跳过解包，不换版本号已装的人根本收不到），
   否则用户看不到新版本。现在目录是仓库里的静态配置文件、由定时任务刷新，
   某个插件发新版只动**它自己那一个文件**。
